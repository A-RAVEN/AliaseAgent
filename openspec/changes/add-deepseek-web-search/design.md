## Goals / Non-Goals

**Goals**

- 配好 DeepSeek 模型的人，**不需要再配任何搜索密钥**就能有 `web_search` 工具。
- 搜索结果与现有两个后端**同一套结构**（网址、标题、日期、摘要），上层与界面不用为它写分支。
- 快、可靠、可核：一次搜索一次请求，拿到结构化结果就返回；拿不到结构化结果就**明确报错**，不拿模型写的文字冒充结果。

**Non-Goals**

- **不取那段"模型写的回答"**。理由见决策 D3 —— 这不是省事，是参考实现与本项目都要的取舍。
- **不把搜索结果塞进会话的流式装配链**（不在会话请求里带服务端工具、不保存也不回传搜索结果块）。这条路要动已经调好的流式装配与工具回传，代价与本变更要解决的问题无关。
- **不做一次请求连搜多轮**（`max_uses` 固定 1）。
- 不改 `web_search` 对模型暴露的参数与返回结构；不改 zhipu / kimi。
- 不做免费搜索的其它路线（浏览器当搜索、SearXNG 之类），那是另一些条目。

## Decisions

### D1 做成 `web_search` 的第三个后端，不另开一个工具

现有搜索后端接口（`sidecar/src/search_provider.h` 的 `ISearchProvider`）正好是这个形状：给它一个查询、一个深度、一个条数上限，回一组 `{title, url, content}`。zhipu 与 kimi 都在这个接口后面。DeepSeek 搜索**接在同一个位置**，于是：模型看到的还是同一个 `web_search`；聚合、并行、命名空间这些现成逻辑都不用动；界面也不用加分支。

**被否决的替代方案**：把搜索结果塞进会话请求里（照参考实现那条路）。否决理由是代价与收益不成比例：要在流式装配里认出 `server_tool_use` 与 `web_search_tool_result` 两种新块、要把它们原样保存、下一轮原样回传（本地文档明确写过：带 `web_search` 工具调用的那一轮，后续消息里必须有对应的结果块，否则报错），而我们已经有一条为普通工具调用调好的链。收益只是"模型能在同一次生成里直接读到搜索结果"。

### D2 凭据默认复用会话模型那把，也允许单独配

`search.deepseek` 段是**可选**的：

| 键 | 缺省 | 含义 |
| --- | --- | --- |
| `api_key` | 缺省不用，回落复用 | 单独指定搜索用的密钥 |
| `base_url` | 缺省不用，回落复用 | 单独指定搜索用的地址（默认取会话模型的 provider 地址） |
| `model` | `deepseek-v4-flash` | 搜索那次调用用的模型 |

**复用的规则**：会话模型当前的 provider 是 Anthropic 兼容端点（本项目默认就是 `https://api.deepseek.com/anthropic`）时，把它的密钥与地址交给搜索后端；`search.deepseek` 里写了就用写的。两处都没有密钥时该后端**不可用**（不报错、不出现），与现有两个后端"没配就不出现"的行为一致。

**为什么允许单独配**：密钥与地址可能不是同一把（例如模型走代理、搜索走官方）。参考实现也把搜索端点与聊天端点的配置分开，并在文档里明确写过"绝不复用聊天那套地址变量"。

### D3 不取模型写的那段回答（这条要写清理由，因为它是本变更最容易被质疑的取舍）

服务端返回里有一个 `text` 块，是搜索模型读完网页自己写的一篇回答（实测约 1900 字，分小标题、像模像样）。**我们不用它**：

1. **参考实现也不用** —— 它的映射函数没有任何字段把这段文字带出去，文档原话是"提供方文本不作为答案受到信任"。也就是说"丢掉它"不是我们独有的偷懒，是这套接口的常规用法。
2. **实测现场支持这个判断**：我那次查询是中文，搜索模型收到的是 `????`（编码没过去），**它照样在没看懂问题的前提下写了一整篇"结论"**，还在末尾提了一句"你的查询里有 `????`"。这种文字真假混在一起，我们没法核。
3. **它不便宜**：那 1112 个输出 token 里就有它。要"留着"不是留着，而是得把它喂给会话模型，那就等于回到 D1 被否决的那条路。
4. **可核的部分我们全留**：网址、标题、日期、引用片段 —— 每一条都能点开自己核。

**这条的边界要说明白**：如果以后有人需要"模型读完网页的结论"，那不是本变更，而是"把服务端搜索接进会话"那个变更要解决的问题；那时这段文字会以正确的形式（连同结果块一起）出现。

### D4 摘要可能为空：放宽旧约定并用标题兜底

现有的搜索结果结构约定"正文必须非空"（`SearchResult.content` 的注释写着 shall be non-empty）。DeepSeek **只在有引用时才给片段**，实测那次一条都没有。处理：

- 有 `cited_text` 就按网址对应上去当正文（与参考实现同规则）；
- 没有就**用标题兜底**，标成"没有摘要"，不让这条结果凭空消失；
- 同时把 `SearchResult.content` 的注释改成"可能为空"，并说清"空"的含义。

**为什么不直接塞一句假摘要**：那会让"摘要为空"这件事在界面上看不出来。宁可如实空着。

### D5 HTTP 用现有工具，不引新依赖

`zhipuai_search.cpp` 与 `kimi_search.cpp` 都是直接用 `libcurl`（`#include <curl/curl.h>` + `curl_easy_init()`），仓库已经链了 curl。新的后端照这个来：一次 POST、带 `x-api-key` 与 `anthropic-version: 2023-06-01`、**不流式**（拿整包 JSON 自己解析，因为我们要的是结构化的结果块，不是逐字文本）。

**要设超时**：参考实现没有明确的超时数字可抄，本后端按现有搜索后端的做法给一个固定秒数（与 zhipu / kimi 同量级），到点算失败。

### D6 服务端搜索次数固定 1、条数我们事后截断

请求里 `max_uses` 固定 1：这个数字是**服务端自己连搜几轮**的上限，每一次都要花钱，所以不给它连搜的机会。`max_results` 由我们在映射之后按顺序截断（服务端没有这个旋钮，实测一次给 10 条）。

**被否决的替代方案**：把 `max_uses` 做成配置项放开。否决理由：这等于把"一次搜索烧掉几轮模型调用"变成一个没人算得清的旋钮；先把 1 做出来，真需要再说。

### D7 失败怎么报

| 情形 | 行为 |
| --- | --- |
| 两处都没有密钥 | 该后端不出现在可用清单里（与现有后端一致），不报错 |
| 地址或密钥不能用、网络失败、HTTP 非 200 | 该后端返回一条错误，带上**它实际用的地址**（好让人看出是端点配错了而不是查询写错了） |
| `HTTP 200` 但返回里**没有**结构化的搜索结果块 | **明确报错**，不回退成"把模型写的文字当结果"。参考实现也是这么做的（它为此专门抛错），理由是不这样做就会把"搜索压根没触发"伪装成"搜到了但没结果" |
| 有结果块但里面一条可用结果都没有 | 正常返回空结果，由上层显示"没搜到" |

### D8 一处本机已知的坑要测到

实测那次返回的 10 条里，有一条标题是**乱码**（韩文站点按 UTF-8 传回，标题字段被打错），三条 `page_age` 全空。所以：

- 标题里的非法字节不能让整个解析崩掉（转成替换字符即可，仓库里已有同样的做法可参考）；
- `page_age` 为空是正常情况，不是错误。

## Risks / Trade-offs

- **成本**：一次搜索 = 一次完整模型调用（实测 5.4 秒、约 8000 token）。比现有两个后端贵得多。缓解：`max_uses` 固定 1；用户文档写清代价；**默认仍让它可用**（因为它不需要额外配置，是"没别的后端时的兜底"）。
- **结果质量不完全可控**：标题可能是乱码、日期常缺、摘要常空。这是服务端行为，不是我们的解析错。
- **端点耦合**：默认复用会话模型的地址。如果谁把模型地址换成一个"兼容 Anthropic 但不支持服务端搜索"的网关，这个后端会以 D7 的"没有结果块"报错 —— 那时需要在 `search.deepseek` 里单独指定地址。
- **不可复现的部分如实标出**：`server_tool_use.web_search_requests` 这个用量字段我实测到了，但**计费口径不明**；本设计不拿它当成本结论，成本结论只用实测的输入/输出 token。

## Migration Plan

无数据迁移。`search` 段不写 `deepseek` 时行为变化只有一条：**原来"没配搜索密钥就没有搜索工具"，现在只要会话模型用的是 Anthropic 兼容端点，工具就会出现**。回退办法：删掉新后端文件与两处注册即可，`web_search` 与另两个后端不受影响。
