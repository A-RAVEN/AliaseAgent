## Context

### 这份设计要守的规矩（2026-10-05 用户明令，规则全文在 `~/.dsh/AGENTS.md` 第 9 节）

设计 / 规范 / 任务里出现的任何**数量上下限**，必须能追溯到四类来源之一：

1. **用户明说过的要求**（引用原话或指出处）；
2. **产品里已有的数字**（指明文件与常量）；
3. **平台或接口的硬限制**（注明来自哪份文档）；
4. **配置项**（默认值与可配范围写出来，并出现在用户文档的配置键表里）。

写不出这四类中的任何一类 = 凭空发明，不许写进设计。配套两条：**砍内容必须可见**（写明略去了什么、有多少），**可见之后必须可恢复**（给出取回完整内容的办法）。

下面每个决策都按这四类标注来源；**标不出处的数字改为"不设"或"派生"**。

### 消费者是谁（改之前先列出来，逐个说清它要的是什么）

`_formatSearchResultForDisplay()` 的输出只有一个消费者：**发给模型的 `tool_result` 正文**（`main.dart` 里 `parsed['content'] = …` 那一行）。界面卡片走的是另一条路（`_buildResultSections()` → `ToolCallActivity.resultSections` → `ToolCallCard`），那条路实测正常、本次不动。

`DeepSeekSearch::search()` 的返回值有两个消费者：`dispatch_web_search()` 的命名空间聚合，以及日志。改动必须保持 `ProviderResult{results, error}` 的形状不变。

## Goals / Non-Goals

**Goals**

- 五处"砍了不说/说了拿不回"的地方全部变成**可见且可恢复**，或者干脆**不砍**。
- 本次改动引入的每一个数字都能在上述四类里指出处；指不出的改成"不设参数"或"按数量派生"。
- 每条改动都有一条**在缺陷仍在时会失败**的检查，且能在本机跑出来（不依赖联网的痕迹留在手工验收里）。

**Non-Goals**

- 不改 `web_search` / `web_fetch` 对模型暴露的参数与返回结构（模型看到的工具定义一个字不改）。
- 不动界面上那条已经正常的结果渲染路径（`_buildResultSections()`）。
- 不放开用户上下文预算：这段文本仍然要有上限，只是**上限不许再是拍脑袋的数**，且越界必须交代清楚。
- 不处理 `add-deepseek-web-search` 之外的老账（例如 `searxng` 被直接标为不可用、`docs/known-bugs.md` 里那两条）。
- 不引入新的外部依赖。

## Decisions

### D1 `max_tokens`：不设这个参数，改为读 `stop_reason`

**做法**：`deepseek` 搜索的请求体里**不再出现 `max_tokens`**；返回里读 `stop_reason`，等于 `"max_tokens"` 时（本地文档原文：`Docs/AnthropicAPIDoc.md` 第 1.5.1 节「`"max_tokens"`: we exceeded the requested `max_tokens` or the model's maximum」；同一节还列出 `"model_context_window_exceeded"`）**这次搜索算失败**，说明里写清"输出被截断、本次结果可能不全"，并把实际读到的 `stop_reason` 一起报出来。

**为什么**（四类来源）：来源③平台默认 —— `Docs/DeepSeekAPIDoc.md`：「取值范围为 1 到 384K（393216）。未设置时，非思考模式默认 8K」。不设参数 = 用平台的 8K 默认，比 2048 宽 4 倍，且**没有任何我发明的数字**。`stop_reason` 这一条的来源是本地文档的字段表与取值说明（来源③）。

**被否决的替代方案**：①沿用参考实现的 4096 —— 那是别的产品的取值，与我们的返回体量（10 条结果约 2400 token）没有推导关系；②把 2048 改成 8192 写死 —— 仍是魔数，只是大一点；③把 `max_tokens` 做成 `search.deepseek.max_tokens` 配置项 —— 用户没法为一次内部调用估这个数，多一个旋钮就是多一个要维护的东西。按台账第 22 条的三条准入（量的单位就是被保护的资源、阈值由模型容量派生、触发后降级而不是停摆），**不设 + 读 stop_reason** 比"设一个我编的数"更接近"阈值由容量派生"。

### D2 响应体上限：保留一个上限，但越界必须交代清楚

**做法**：写回调超限时不再只是 `return 0`，而是记录**已收到的字节数与上限**，中止后返回一条失败说明：「响应超过上限 16MB（已收到 N 字节），本次结果不完整」。上限取多少暂不改，但要在代码注释里写清它是"防内存爆掉"的保护，而不是内容预算。

**为什么**：这是**内存保护**，不是内容裁剪 —— 按四类来源它算"产品里已有的数字"（`sidecar/src/web_fetch.cpp` 里有同类的大小保护），本次只补"可见"这一半。**不许**把它当成可以随手调整的内容旋钮。

**被否决的替代方案**：①直接删掉上限、无限收 —— 一个坏掉的端点能把进程吃爆；②改成流式解析（边收边扔）—— 收益与本次要解决的问题无关，且要动整个传输层。

### D3 拼给模型的搜索结果：先保证每个后端都露面，预算按数量派生

**做法**（顺序固定）：

1. 第一遍只写每个后端的**结果行**（`<后端名>: <条数> results`，出错的写 `ERROR — …`）——**这一遍不参与预算判断**，因为一行几十字，后端数量是用户配置决定的、天然有界；
2. 第二遍把**剩余预算**（总量减去结果行占用的字符）**按后端数量均分**，每个后端用自己的那份写它的首条结果预览（`标题 — 网址` + 截断到该份额的正文）；
3. 因为结果行不再被砍，"有三个后端却只看到一个"这类**结构性丢失**从实现上不可能再发生；
4. 若某个后端的预览份额小于一个最小值（算出来放不下"标题 — 网址"），**不写预览但必须写一行标记**：「（本条预览因篇幅未显示，结果 N 条）」；
5. 确实还有后端整段没写时，收尾的标记要说清**是哪些后端、各多少条**（现在的标记只说"还有 N 个后端没显示"，按统一规则不够 —— 见 `truncation-visibility` 那条"结构性丢失一律不许发生"）。

**为什么做**（第一轮对抗验证后改写过）：**不是**因为"超了不标记"（复算证明标记会触发），而是因为**第一个后端的预览会把预算吃满、后面的后端整段消失**，而且消失时那条标记**说不出丢的是谁、丢了多少条**。

**总量这个数字怎么办**（这是本次唯一必须保留的预算）：它**不是**用户要求（用户 2026-10-05 明说 2000 不是他的要求），也不是平台硬限，因此按规矩它**只能来自产品里已有的数字或配置项**。本设计选：**沿用产品里已有的 `kToolResultElisionThreshold`（8000）作为派生上限** —— 这段文本拼完由 `_elideOversizedToolResult()` 统一过一遍通用截断，所以"拼装预算 ≤ 通用阈值"是必须成立的不变量；实现里让预算**引用同一个常量**，并在注释里写明这条不变量。

**这条不变量怎么验**（第一轮对抗验证指出原计划的 4.3 恒真，第二轮又指出"喂入规模根本触发不到省略分支"，两处都已改）：因为两边是同一个常量，"两者是否相等"永远为真、构造不出失败；而按 4.1 的拼法，三个后端各 5 条、每条 900 字的喂入只拼出约 900 字，远低于 8000，**"有后端被省略"这条分支根本不会发生**，标记断言同样恒真。所以：

1. 把拼装逻辑抽成**可传入预算的纯函数**（`装配(results, 预算)`），生产路径传入 `kToolResultElisionThreshold`；
2. 用例分两层：①**生产预算那一层**（`test/integration`，经假 sidecar 的 `lastMessagesJson`）断言"三个后端名都在"，喂入用它自己的真实规模；②**小预算那一层**（纯函数用例）传一个必然越界的预算，断言"标记里点名了哪些后端、各多少条"从"有后端被省略"这一支真的跑出来了；
3. 这样两条分支各有能失败的断言，不再依赖"喂多大的数据才刚好触发"。

**被否决的替代方案**：①把 2000 直接改成 8000 —— 还是魔数，只是换了个大的；②不设预算、拼多长算多长 —— 会撞上通用截断，等于换个地方丢；③新增 `search.preview_chars` 配置项 —— 用户没法估这个数（同 D1 的否决理由③）；④靠"喂一份刚好超 8000 的数据"来触发省略分支 —— 那种用例的成败取决于喂入规模，实现稍改就悄悄变成恒真（第二轮对抗验证正是这么发现原 4.3 恒真的）。

### D4 `web_fetch` 的再取路径：标记里带原网址

**做法**：`_elideOversizedToolResult()` 的再取片段按**可用输入**拼：有 `path` 用 `path`（沿用现在的行为），否则有 `url` 就用 `url`，两者都没有时**明确写"本篇无法自动再取，请重新给出网址"**，不许留空。

**为什么**（四类来源）：来源①规范条文 —— `openspec/specs/context-compaction/spec.md` 的 `Near-zone oversized tool_result body elision` 要求把超大正文裁成「a truncation marker plus a refetch record」（`_elideOversizedToolResult()` 就是它的实现，`lib/main.dart` 里那段注释也点名了这条规范）；来源②产品已有 —— 同一个函数的 `path` 分支就是现成形态。本次只是把它推广到 `web_fetch`，并把"两者都没有"这一种情形也交代清楚。

**更正**：本设计初稿把这个出处写成「`add-command-tool` 的规范里写明"截断标记 + 再取记录"」，**这是错的** —— 那句话出自 `add-auto-context-compaction`（已归档），`add-command-tool` 的规范里没有这句。出处指错等于没有出处，第一轮对抗验证把它挑出来了。

**被否决的替代方案**：给 `web_fetch` 加一个 `path` 参数只为了让标记好看 —— 为拼一个提示而改工具接口，代价与收益不成比例。

### D5 启动就绪：工具清单装好之前，发送入口不许放行

**做法**：`ChatScreenState` 增加一个"工具清单已就绪"的状态；`ChatArea` 增加对应的入参（缺省 `true`，保证既有窗口用例行为不变）。未就绪时**发送按钮禁用并给出可见文案**（工具提示写"正在准备工具…"），就绪后恢复。**不做静默排队**：排队的消息在用户看来还是"发出去了"，只是晚了几秒，出问题时更难解释。

**为什么**（四类来源）：来源①缺陷事实 —— 启动窗口期发出的那一轮，清单里**缺**动态加入的那批工具（`web_search` / `web_fetch` / 浏览器四件套），模型因此无搜索工具可用（真机那次一个工具都没调）；来源②产品已有 —— 发送按钮本来就有 `isStreaming` 这一道禁用条件，本次是同一形态的第二个条件。

**被否决的替代方案**：①允许发送但在发送时 `await` 就绪 —— 用户按了发送却没有任何反馈，比禁用更糟；②只改真机用例里的等待 —— 那正是我上一轮干的事，被用户当成"绕过"，本次不许。

### D6 "可见 + 可恢复"落成一条通用规则，而不是五处各说各话

新增能力 `truncation-visibility` 把这条规则写成可验收的要求（标记必须存在、必须含"略去了什么/多少"、必须含一个可执行的取回入口），五处实现各自落到这条规则上。这样将来再加工具时，检查的是同一条规则，而不是又一次凭手感。

**这条规则与已有规范的关系（第一轮对抗验证后补，原稿漏了）**：

```
                     ┌──────────────────────────────────────────┐
                     │  truncation-visibility（本次新增，总规则）│
                     │  标记必须存在 / 说清略去什么多少 / 可恢复 │
                     └───────────────┬──────────────────────────┘
                                     │ 收编（而不是另立一套）
        ┌────────────────────────────┼────────────────────────────┐
        ▼                            ▼                            ▼
┌───────────────────┐   ┌───────────────────────┐   ┌──────────────────────┐
│ context-compaction │   │      file-search       │   │  deepseek-search-     │
│ Near-zone elision  │   │ glob_file / grep_file  │   │  provider             │
│ 已要求"截断标记 +  │   │ 现在只有 truncated:true │   │ 请求体原写"必须含     │
│ 再取记录"          │   │ 不说略去多少、无入口    │   │ max_tokens 固定上限"  │
│ ⇒ 本次给 delta，把 │   │ ⇒ 本次给 delta，要求    │   │ ⇒ 本次给 delta，删掉  │
│ 取回形态统一        │   │ 补"略去多少 + 入口"     │   │ 该要求并加 stop_reason│
└───────────────────┘   └───────────────────────┘   └──────────────────────┘
```

四处要点：

1. **`context-compaction`**：已有的 `Near-zone oversized tool_result body elision` 要求「a truncation marker plus a refetch record」，`_elideOversizedToolResult()` 是它的实现。本能力**不另立形态**，而是给那份规范一份 delta，把"取回记录"的形态写清（有 `path` 用 `path`、否则用 `url`、都没有就明说取不回），让两份规范说的是同一件事。
2. **`file-search`**：`glob_file` / `grep_file` 现在只回 `"truncated":true`，不说略去了多少、也没有取回入口。本能力的总规则说"适用于任何工具结果"，所以必须给它 delta，否则同一条规则在两处强度不同。
3. **`deepseek-search-provider`**（上一轮刚写完、还没归档的那份）：它写着请求体**必须**含 `{"max_tokens": <固定上限>}`，而 D1 要删掉该参数 ⇒ 不给 delta 就是两份规范直接打架。
4. **`stop_reason` 要写进规范**：原稿只把这条要求写在 design 与 tasks 里，四份 spec 里 `stop_reason` 零命中 —— 规范覆盖不到就不算要求。

## Risks / Trade-offs

- **D1 的代价**：不设 `max_tokens` 后，极端情况下模型可能生成很长的输出（服务端上限 384K），一次搜索耗时与费用上升。缓解：搜索提示词要求它返回结构化结果；实测同类请求输出 620~1112 token。
- **D3 的代价**：预算分给多个后端后，单条预览可能变短。缓解：结果行永远完整、预览有明确的"未显示"标记；界面那条完整渲染路径不受影响。
- **D5 的代价**：启动后极短时间内发送按钮不可用（本机实测就绪耗时约 2 秒）。缓解：给出可见文案；这是"少做一点"，不是"停摆"。
- **不可复现的部分如实标出**：D1 的 `stop_reason` 截断分支与 D2 的体积越界在本机**无法用真机稳定触发**（要造一个超长输出或 16MB 响应）。所以判据放在离线层：`stop_reason` 走 `map_response()` 的纯函数（喂响应文本），体积越界走**抽出来之后**的可注入判定函数（这正是 3.2 那条前置任务存在的原因），真机只做一次正常搜索确认没有回归。
- **模型看到的那段文本怎么读**（判据的出口，第一轮对抗验证后确认）：假 sidecar（`test/integration/helpers/fake_sidecar.dart`）记录了 `lastMessagesJson`，也就是**发给模型的整包消息**，里面就有 `tool_result` 的正文 —— 所以 D3/D4 的行为断言可以在 `test/integration` 里做，不需要去够一个私有方法。
- **本次不改的既有欠账**：`const maxLen = 2000` 那个常量本身会随 D3 消失；`e0a8143` 里同批引入的 `nsCount`（已确认是个没用的计数，`flutter analyze` 一直在报它）一并清掉；`docs/known-bugs.md` 里与本次无关的条目不动。
