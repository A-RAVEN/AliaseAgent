## Context

**现状（2026-10-03 读代码核实；指针写函数名，不写行号）**：

- 一级摘要的输入只有本批消息：`ModelSummaryProvider.summarize` 把 `folded` 逐条渲染成 `role: 文本`，末尾追加常量 `kSummarizeInstruction`，system 是一句通用的"你是 AliasAgent 的对话摘要器"。**它看不到任何更早的内容。**
- 二级合一的输入是它这次要合并的那几条一级摘要（`summarizeText(text: …join('\n\n'))`）——它本来就"看得到前文"。**但 `summarize` 有两个调用点**：折叠路径 `_resolveOpenLevel1`，以及二级保底路径里的 `_l1SummaryText`（它的产物正是二级要合并的输入）。本变更只给前者传参考。
- 摘要调用的返回里**两个数都有**：`onDone(code, err, stop, inTok, outTok)`，但两个方法只接 `outTok`（作为摘要的实测大小），`inTok` 丢掉；`SummaryResult` 也只有 `text` + `tokens`（输出大小）。
- 摘要的输出长度**由模型/接口默认值决定，本项目不设上限**：sidecar 的摘要分支不带 `max_tokens`（源码注释写着 "The request now carries no max_tokens at all, so the model/endpoint default applies"），主规范场景 `Summary output length is model-governed` 写着 "its output length is not capped by a compaction-design constant"，`TODO.md` 顶部也把写死的 `max_tokens 1024` 记为已删。**代码里仍留着四处过期注释**说"上限 1024"（`model_summary_provider.dart` 三处、`summary_provider.dart` 一处），本变更顺手改对（否则下一个人会照抄）。另有一处同名注释在 `seam_selector.dart`，那是本变更之外的文件，另立任务处理，不在本变更里改。
- 输出大小是**判断摘要是否合格**的唯一量：一级"必须比它替换掉的原文小"、二级"必须比它替换掉的那几条一级小"，都靠它；一级不合格时走"折半重压"（同一批会被拆成两半、多花一次调用）。
- 已有相关设施：`GuardAnchors`（用户钉死的要求，每轮重新注入主模型，从不折叠）解决的是"别丢硬约束"，与"让摘要器读懂前文"是两件事，不能互相替代。
- 摘要出现在投影里的形态是固定的：一级 `## 更早上下文(压缩xN,非用户发言)`、二级 `## 更早上下文(压缩xN,层级2,非用户发言)`，本变更一个字都不动。
- 假替身侧：`FakeSummaryProvider` 现在只记 `lastFolded`，**不记它收到的参考**；`ModelSummaryProvider` 有现成的 provider 级用例写法（`test/unit/model_summary_provider_test.dart` 用 `FakeSidecar`），它能直接给 `inputTokens`，也能读回 `lastSystemPrompt` / `lastMessagesJson`。

**约束**：

- 用户 2026-10-03 裁定：**摘要文本的质量不设自动判据**（摘要结果与模型本身关系很大，设阈值只会得到一条天天误报或天天沉默的判据）；质量改成跑完 live 后人工看一次并如实记录。
- 调用时点上**拿不到"当前投影"**：投影表是在这一趟的段循环之后才建的，`_resolveOpenLevel1` 的入参里既没有会话 id、也没有已载入的摘要。参考只能从库里取，取候选的时机与过滤条件必须写死（见 D1）。
- 用户钉死的规则一条都不能碰：只设 token 数阈值、阈值由模型容量派生、一级与二级摘要不许有内容重复、只有位置足够靠后时才用摘要替换原文、攒够阈值就压。

## Goals / Non-Goals

**Goals:**

1. 让写一级摘要的模型知道**前面发生过什么**，从而能解析本段里的指代、不必重述用户目标、能写清"为什么换方案"。
2. 参考的体量**有界**：不随会话变长而增长。
3. 参考与待压缩原文在请求里**明确分开**，并有硬要求禁止把参考写进摘要。
4. 每次摘要调用**发了多少 token 看得见**（加了参考之后多花多少，事后能回答）。
5. 第一段摘要（没有更早摘要可参考）的行为与今天**一字不差**。

**Non-Goals:**

- **不做文本相似度闸门**：不因为摘要文本与参考相似而判失败、重试或重写（用户裁定）。既有的"同一段不许两种表示"这类结构检查不受影响，照旧生效。
- 不改阈值 / 投影分档 / 何时压 / 何时等这四件钉死的事。
- 不改二级合一那条链的输入：`_l1SummaryText`（二级保底路径）**不接参考**，`summarizeText` 也不接。
- 输入 token **不落库**（只进观测通道）；不做跨会话的成本统计。
- 不改摘要投影时的标记与顺序，也不在代码里改写摘要文本（不做"自动消解指代"这类后处理）。
- 不给"参考哪条最相关"做检索或相似度挑选：固定取"最近的一条一级 + 层级最高的那条"，与段的相关性不作保证。

## Decisions

### D1 参考从库里取，固定两条，按覆盖范围去重

- **取候选的时机与来源**：在 `_resolveSummariesInner` 里、这一趟开始折第一段之前取一次快照 —— 用 `SummaryNodeRepository.queryBySession(sessionId)` 读已落盘的摘要节点（含 `level`、`coveredMinSeq`、`coveredMaxSeq`、`summaryJson` 文本）。**库没打开（`dbOpen` 为假）或查不到任何节点时，参考为空**，整条路径退化成今天的行为。
- **过滤**：只留 `coveredMaxSeq` **严格小于本批最旧序号**的节点（覆盖范围与本次批次有交叠的一律排除）。这样就天然排除了"本趟后半段才合成、还没进投影"的二级摘要。
- **选哪两条**：①这些候选里**最近**的一条一级（管局部衔接）；②候选里**层级最高**的一条（通常是二级；管全局目标与硬约束，不保证它是二级）。每条都带上自己覆盖的序号范围。
- **按覆盖范围去重**：若较细那条的覆盖范围被较粗那条**完全盖住**，只带较粗的那条 —— 同一段历史不以两种文本进同一次请求。这时失去的是"紧邻上文"的连续性，但那段历史本来就被较粗那条覆盖着。
- **"本批"在折半递归里怎么算**：参考在折半之前算一次，两半**用同一份**参考；过滤用的"本批最旧序号"取**最外层那一批**的最旧序号。`_resolveOpenLevel1` 需要新增的入参：会话 id、库是否打开，以及已选好的参考列表。
- **为什么是有界的两条**：参考的成本是每次摘要调用的**输入 token**，而输入随会话长度增长就是无界开销；喂"全部更早摘要"会让每次折叠都重读越来越长的历史。**摘要的输出长度不受本项目限制（由模型/接口默认值决定），所以多喂输入买不到"更长的摘要"**，只买到"更可能抄旧账"。
- **否决"只喂最近一条"**：长会话里用户目标可能是七八段之前定的，只喂最近一条解决不了指代悬空 —— 这正是要修的东西。
- **否决"按相似度挑最相关的几条"**：要引入检索与相似度阈值，代价与不确定性都上一个台阶，而收益只有一条人工观测量兜底。

### D2 提示词分块：参考与原文分属不同消息，各带抬头（**只在这一趟有参考时才出现**）

有参考时（自前向后）：

```
system : <今天那两句原文> + 用户消息里会给你一段【参考上下文】和一段【待压缩原文】；
         参考只用来解析指代、判断"什么已经说过了"，严禁把它的内容写进摘要。
user   : 【参考上下文 · 不要总结】<第 N..M 段摘要>…
user   : 【待压缩原文 · 只总结这一段】<本批消息逐条渲染>
user   : <原有 kSummarizeInstruction>
```

没有参考时：**system 就是今天那串原文**（不含禁令句），消息就是今天的样子（本批逐条成消息、无任何抬头）、末尾仍是 `kSummarizeInstruction`。**两条路径的这一句都要照抄原文写进任务，判据用硬编码断言**，不许靠"手抄一份改前的 stdout 来对比"。

- **为什么分消息**：混在同一条消息里，模型无法可靠区分"哪些是要总结的、哪些只是背景"；抬头 + 分消息是唯一稳的分隔方式，也让用例能用确定性的方式断言"两块没混在一起"。
- **为什么输出要求仍殿后**：现有实现就是最后一条 user 消息承载指令，位置不变可以少动一处既有约定。
- **否决"把参考塞进 system"**：参考内容每段都不一样，塞进 system 会让 system 不再是稳定的角色说明，也会让"参考与原文分开"失去可断言的对象。

### D3 输入 token 只进观测通道，落点在 provider 内部

- `SummaryResult` 增加输入 token 字段；`ModelSummaryProvider.summarize` 与 `summarizeText` 各自把 `inTok` 接住，并各自打一行 `[OBS] summary in=…/out=…`（用 `debugPrint`，测试侧有现成的捕获写法）。
- **落点为什么放在这两个方法里**：`main.dart` 里有四个调用点（一级折叠、二级保底路径、2-pass 合一、收拢循环），放在 provider 内部一处覆盖四个，漏打不了；也天然满足"不进模型可见内容"。
- **为什么不落库**：`summary_nodes` 只有一列 `token_cost`（存输出大小），要加列就得改建表语句、模型、仓库和四处 `materialize` 调用点，还要定"库里已有的旧行怎么算"。本变更只需要回答"这一次多花了多少"。
- **何时可以重新考虑落库**：真要按会话统计压缩总开销、或按开销做告警时，再加列并写迁移。

### D4 机器判据只覆盖"机制"，每条都要能失败

1. 输入 token 有读数：provider 级用例分别驱动两个方法，两次都读到 `in=` 行，且值等于假 sidecar 给的那个数。
2. 参考确实被算出来并**真的传到了 provider**：给 `FakeSummaryProvider` 加一个记录参考的字段，集成用例断言它收到的正是"最近的一条一级 + 层级最高那条"（光测纯函数不算 —— 纯函数写对而一处都不接线时会假绿）。
3. 参考与原文分属不同消息：provider 级用例断言 `lastMessagesJson` 里两条消息各带自己的抬头。
4. 没有参考时与今天逐字相同：provider 级用例断言 `lastSystemPrompt` 等于今天那串原文、消息条数与内容与今天一致（硬编码断言，不靠手抄 stdout）。
5. 提示词里确实有禁令句：断言有参考时的 `lastSystemPrompt` 同时含今天那两句与禁令句。

摘要文本本身（有没有复述、指代有没有解开）**只由 live 跑完后人工看一次**并如实记录，不作通过/失败判据。**如实说明**：既有的 `integration_test/compact_quality_live_test.dart` 自带一条"摘要必须保住再执行钥匙"的判据，它判的是摘要文本、会在质量崩掉时红 —— 那是**改动前就有的既有判据**，不是本次新增，也不因本次裁定而取消。

### D5 没有参考时与今天一字不差

第一段摘要（以及任何取不到更早摘要的折叠）走今天的路径：不加参考消息、system 与今天逐字相同、消息形状与 `kSummarizeInstruction` 的位置都不变。这条保证既有用例的前提不变，也让回滚面最小。

## Risks / Trade-offs

- **[模型抄旧账：把参考的内容复述进新摘要]** → 提示词里有明确禁令，但**没有自动判据**（用户裁定）；后果是摘要变长、内容重复。缓解：live 跑完人工看一次并如实记录；将来真在实际使用里看到重复，再重新考虑加闸门（届时先把"相邻摘要本来就有的重合度"量出来当基线）。
- **[摘要可能比过去更长]** → 输出长度不受本项目限制（模型/接口默认值决定），多喂输入不保证摘要不变长；一级"实测不小于被替换内容就折半重压"会把"变长"变成更多次摘要调用。本变更不做长度控制，只让成本可见。
- **[成本上升且只事后可见]** → 每次折叠的输入多两条摘要（几百到上千 token 量级，未实测）。本变更只让它**可见**（`[OBS] summary in=`），不做上限、不做告警。先有读数，再谈控制。
- **[参考里的旧错误被引用延续]** → 参考是更粗的摘要，它自己就可能漏或错。缓解：提示词只说参考用于解析指代与判断已说过的内容，不要求把参考并进摘要；不引入"以参考为准"的措辞。
- **[层级最高那条与本段无关]** → 固定取"层级最高"，可能取到一段与本批无关的历史。缓解：参考块带序号范围让模型自己判断；提示词写明"参考与本段无关就忽略"。不引入相似度挑选（见 D1）。
- **[参考过时或与本次批次交叠]** → 由 D1 的过滤条件（覆盖范围严格早于本批）与按覆盖范围去重挡住；这两条都要有用例兜住，不能只写在设计里。

## Migration Plan

1. 先加读数（D3）：`SummaryResult` 带输入 token、两个方法接住并打观测行；provider 级用例确认两次调用都读得到。这一步不改变任何请求内容。
2. 把五处"上限 1024"的过时注释改对（`model_summary_provider.dart` 三处、`summary_provider.dart` 一处、`seam_selector.dart` 一处）。
3. 再加参考块（D1 + D2）：先写"取候选 + 过滤 + 按覆盖范围去重"的纯函数，再把它接进 `_resolveSummariesInner` / `_resolveOpenLevel1`，最后改提示词布局（有参考 / 无参考两条路径）。
4. 集成与 provider 级用例把 D4 的五条判据补齐。
5. 验证：`flutter analyze`、全量 `flutter test`（先同步 DLL）、live（跑完用 `read_image` 读图 + 人工看摘要质量并如实记录）、整套冒烟（失败项与改动前一致、不得新增）。
6. 回滚：还原 `model_summary_provider.dart`、`summary_provider.dart` 与 `main.dart` 三处即回到今天的行为（无参考路径与今天逐字相同，D5）。

## Open Questions

1. **参考块要不要带"这条摘要覆盖的序号范围"？** 倾向带（成本几乎为零，能帮模型判断相关性，也是按覆盖范围去重的依据）。若实测发现模型会把它写进摘要正文，就退回不带。
2. **要不要在参考里带上"这段之后发生了什么"（本批的下一段）？** 本变更不做：摘要只往回看，向前引用会让"摘要与它覆盖的范围"解耦，也会让不同批次的摘要在重压时互相漂移。
