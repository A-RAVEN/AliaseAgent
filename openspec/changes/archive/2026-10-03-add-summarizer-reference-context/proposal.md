## Why

一级摘要现在是"闭着眼睛"写的：`ModelSummaryProvider.summarize` 只把**这一批消息**加一段固定的"必须保留什么"指令发给摘要模型，它看不到任何更早的内容。后果有三个：相邻摘要之间**指代悬空**（"把它改回 5 秒"里的"它"在本批里没有先行词）、每段都**重述一遍用户目标**（于是段与段互相重复）、**前因后果断线**（这一步为什么换方案，要靠上一段才读得懂）。

同时这次优化的代价现在看不见：摘要调用返回的输入 token（`onDone(..., inTok, ...)`）拿到就丢掉，`SummaryResult` 只带输出大小 —— 参考上下文喂进去之后"多花了多少"无从回答。

## What Changes

- **摘要请求带一个有界的参考上下文**：从**已落盘**的摘要里取最多两条 —— 最近的一条一级摘要 + 层级最高的那条（通常是二级，不保证是）；只取覆盖范围**严格早于本批**的（与本次批次交叠的一律排除，例如本趟后半段才合成的二级），并**按覆盖范围去重**（较细那条被较粗那条完全盖住时只带较粗的）；取不到时（第一段摘要、或摘要库没打开）请求与今天一字不差。
- **提示词分块，参考与原文明确分开**：参考上下文单独一条消息、带"【参考上下文 · 不要总结】"抬头；待压缩原文单独一条消息、带"【待压缩原文 · 只总结这一段】"抬头；**有参考时** system 在保留今天那两句（忠实、精简；与对话正文相同的语言）之外，追加"参考只用于解析指代与判断什么已经说过了，禁止写进摘要"；原有的输出要求（`kSummarizeInstruction`）仍殿后。**没有参考时这条分支整条不发**，system 与消息形状都是今天的原文。
- **摘要调用的输入 token 进观测通道**：`SummaryResult` 带上输入 token，`ModelSummaryProvider` 的两个方法各自打一行 `[OBS] summary in=…/out=…`（落点在 provider 内部，一处覆盖 `main.dart` 的四个调用点）；不落库、不进模型可见内容、不参与"摘要是否合格"的判断。
- **明确不做自动的复述闸门**：摘要文本与参考上下文像不像，**不判失败、不重试**（用户 2026-10-03 裁定：摘要质量与模型本身关系很大，设阈值只会得到一条天天误报或天天沉默的判据；质量改成跑完 live 后人工看一次并如实记录）。
- 二级合一的输入不动（它本来就看得到自己要合并的那几条一级摘要）。

## Capabilities

### New Capabilities

（无）

### Modified Capabilities

- `context-compaction`：新增两条要求 —— ①摘要请求携带一个**有界**、与待压缩原文**分开**的参考上下文，且它对第一段摘要不产生任何影响；②每次摘要调用的输入 token 记进观测通道，并写明"不因摘要文本与参考相似而拒绝或重试"。

## Impact

- **产品代码**：`lib/services/compaction/summary_provider.dart`（`SummaryResult` 增加输入 token 字段；`summarize` 增加参考参数）、`lib/services/compaction/model_summary_provider.dart`（两个方法接住 `inTok` 并各打一行观测、参考上下文拼装、提示词分块、假 provider 记录参考）、`lib/main.dart`（在折叠入口取一次候选快照并逐段传下去；`_resolveOpenLevel1` 新增会话 id 与参考入参）、`lib/services/compaction/seam_selector.dart`（只改一处过时注释）。
- **测试**：单测——假 provider 记录"这次收到哪几条参考"，含首段为空的情形；集成——请求里参考块与原文分属不同消息、system 含禁令句、输入 token 非零且带参考后变大；live——跑一次真实压缩，贴出摘要原文与 in/out 读数，人工看一遍质量并如实记录。
- **文档**：`Docs/user-guide/context-compaction.md` 已写明"生成摘要要走一次模型调用、这一步要计费"，本次按需补一句方向与代价。
- **不做**（明确划界）：不改阈值 / 投影分档 / 何时压 / 何时等；不改二级合一的输入；输入 token 不落库；不做自动复述判据；不改摘要投影时的呈现格式（那三个标记与顺序都不动）。
