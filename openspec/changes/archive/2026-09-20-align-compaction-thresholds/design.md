## Context

**用户钉死的原始要求**（原文在 `TODO.md` 顶部「🔒 钉死的原始要求：上下文压缩的阈值」，本设计受其约束）：**只设 token 数阈值；阈值必须由「模型能装下的上下文总量 × 一个百分比」实时算出（用户举例 25% × 100 万）；不设条数阈值；不写死绝对数；够不着阈值 = 实现有问题，改实现而不是改要求。**

**两个层级的名字（先说清楚，后面全部用这两个词）**：

- **L1 摘要** = 把一段较早的对话压成的一条小摘要。
- **L2 摘要** = 把已经生成的**多条 L1 摘要再合成一条更粗的摘要**（合成动作下文一律写作「合成 L2 摘要」，不用任何简称）。只做这两级。

**现状（2026-09-13 读代码核实，指针为函数/变量名，不写行号）**：

- 阈值派生：`CompactionEngine._batchThreshold(maxContextTokens)` 返回 `maxContextTokens ~/ 2`；收拢循环里 `final T = budget ~/ 2`，而 `budget` 两个调用方传进去的都是 `maxContextTokens`。两处都是写死 50%。
- 合成 L2 的判据：`main.dart` 收拢循环里 `if (consecutiveL1 >= 2 && groupCount >= 2)` —— **先要求"至少 2 条"这个条数门槛**。
- 写死的绝对数：`CompactionEngine._minBatchRaw(T) => max(1, max(T ~/ 2, 1025))`；摘要请求在 `sidecar/src/model_gateway.cpp` 写死 `body["max_tokens"] = 1024`。
- 机制封顶：`_loadClosedSegments` 把库里**所有**节点都载入为"已冻结"；`buildTree` 的注释写明已冻结的段落 `never re-folded or re-shaped`；收拢循环只对"本轮新产出、尚未落盘"的那几条分组 ⇒ **能参与合成 L2 的集合永远只有一次压缩新产出的 1-2 条**，跨轮次根本攒不到阈值。
- 另一处判据缺口：`l2GroupCount(tokens, T)` 在"累加始终没超过阈值"时返回 `tokens.length`，与"真的超过阈值才成组"无法区分 ⇒ 现有代码会在**累计还没到阈值**时也合成（只要有 ≥2 条）。
- **第四处偏离 —— 触发口径**：用户 2026-08-29 定下的统一规则是「**从最旧累计，累计超过阈值就把这一批压一次成上一级**」，**两层同一条**（原文也是攒够阈值就压，不等窗口装满）。但 `_foldTail` 在"还没超出模型容量"时直接返回、什么都不压（`totalProxy <= budget` 那条早退），于是原文只有在**装不下**的时候才会被压。规范那一条也写成"投影达到 `maxContextTokens` 时才压"，与这条统一规则不一致。**⚠️ 我在本变更的第一版里把这处现状当成"原有行为不变"复述，已更正。**
- **第五处偏离 —— 每会话压缩上限**（**审查发现后补记，第一版一字未提**）：`lib/main.dart` 里有 `kMaxFoldsPerSession = 30`（**条数门槛**）与 `kMaxFoldTokensPerSession = 500000`（**与窗口无关的写死绝对数**），判据是 `isFoldBudgetExceeded`（数的是这个会话**已经存下来的摘要条数** —— `summary_nodes` 里 `level >= 1` 且带 token 数的行，每段对话各自的小摘要算一条、合成出来的粗摘要也算一条；节点只增不减，没有重置口）。超限后内联路径整段原文发送、后台压缩直接返回；而合成 L2 唯一的产出点是 `_resolveSummaries`，它只被这两条路径调用 ⇒ **上限一到，"压原文"与"合成 L2"同时永久停摆**。按本设计 D8 的算术，攒到 25% × 100 万 = 25 万 token 的摘要需要远超 30 条节点 ⇒ **真实配置下 L2 依然一次都不会出现**。这处上限必须在本变更里处置（见 D9）。

**实测后果**：受控测试（200 段填充 + 5 条承重消息，共 407 条）只产出 **2 条 L1 摘要**（610 / 626 tokens），**0 条 L2 摘要**；真实库 `~/.aliasagent/aliasagent.db` 的 `summary_nodes` **0 行**。

**约束**：`summary_nodes` 表结构不变（`level` 列已存在）；"某段不进这次的请求 ≠ 删掉它"不变；"已经压过的段落不再重新压一遍"不变；只做两级；不改界面；不改"由 AI 挑选批次分界"的机制。

## Goals / Non-Goals

**Goals:**

1. 阈值全部改为「**模型能装下的上下文总量 × 配置里的百分比 ÷ 100**」，百分比是每个 agent 类型一项配置（`compaction_threshold_percent`，缺省 25）；机制内**不再有**写死的比例、绝对下限或绝对上限。
2. 机制内**不再有任何条数判据**：什么时候触发、一次把几条合成、什么时候停，全部只看 token 量。
3. **两层都真的会压**：从最旧累加，**原文**累计超过阈值就压成 L1 摘要（不等窗口装满），**L1 摘要**累计超过阈值就合成 L2 摘要（不看有没有空余）；并且有测试断言**发给模型的上下文里真的含 L1 摘要与 L2 摘要**。
4. "够不着阈值"这类问题用**能算给人看的数字**暴露出来，而不是含糊成"已知限制"。

**Non-Goals:**

- 不做第三级；不改"由 AI 挑选批次分界"；不改"不进本次请求的内容仍然留在磁盘上"；不改 `summary_nodes` 表结构；不加界面设置项；不重写摘要用的提示词。

## Decisions

### D1 阈值只在一个地方算出来：模型能装下的总量 × 配置百分比 ÷ 100

新增 `CompactionEngine.thresholdTokens(maxContextTokens, percent)` 作为**唯一**的阈值计算点；删除 `_batchThreshold`；分批边界、最新原文保留量、合成 L2 的阈值三处全部调用它。`AgentTypeConfig` 新增 `compactionThresholdPercent`（配置键 `compaction_threshold_percent`，缺省 `25`；缺失 / 不是整数 / 小于等于 0 / 大于 100 时回落到缺省，并打印一次提示）。

**备选与否决理由**：把三种用途拆成三个各自独立的百分比 —— **否，且 2026-09-13 用户已拍板"先不拆"**（保持"只用这一个百分比"，实测发现最近的上下文不够再拆；拆了也仍然都必须是容量的百分比）。用户的要求是"**一个** token 阈值由一个百分比定"，拆成三个就把"唯一旋钮"变成三个没有实测依据的旋钮。**代价如实记入 Risks**：百分比从 50 降到 25 之后，"最新的对话保留原文"的那一块会从模型容量的 50% 缩到 25%；这是**取值**的副作用，不是机制的偏离。

### D2 判据只认 token：没到阈值就返回"不成组"

`l2GroupCount(tokens, T)` 改为：从最旧开始累加，**首次超过阈值时返回这一组有几条**；**累加始终没超过阈值时返回 0**（而不是现在的"返回全部条数"）。收拢循环的判据变成"组数大于 0" —— 删掉 `consecutiveL1 >= 2 && groupCount >= 2` 这个条数门槛。累计没到阈值就不合成；此时若还超预算，走原有的"最旧的不进本次请求"（磁盘上的数据不动）。

**只有一条摘要、而它自己就超过阈值**这种情形：按 token 规则**照常尝试合成**（不再被"至少 2 条"拦下），由既有的实测判据裁决 —— **合成出来的 L2 摘要，实测 token 必须小于被它替换掉的那几条 L1 摘要之和**，否则拒绝并改走"最旧的不进本次请求"。也就是说，原来挡在计数上的事，改由"实测确实变小"来承担，这是判据而不是门槛。

### D3 L1 摘要不再"一落盘就冻结"：冻结的是"不再重新压一遍原文"，不是"不能再合成 L2"

- 载入的持久化节点分两类：两层以上的（L2）→ **冻结**（永远不再作为合成 L2 的输入，只做两级）；L1 → **可以参与合成 L2**（但它的文本仍然**直接复用**，绝不重新去压它覆盖的原文）。
- **两类都仍然算"已经覆盖过这段原文"**：`buildTree` 计算"还没处理的那一截从哪里开始"时，仍然取所有已载入节点的最大覆盖序号，所以原文绝不会被重新压一遍。
- 参与本次请求的条目改成**一张按时间从旧到新排好的表**，每条带"冻结 / 可调整"标记；遇到一条冻结条目就**打断**"连续 L1"的成组（这是结构上的约束，不是条数门槛）。这一步是必需的：现有实现靠"冻结的那批 + 可调整的那批"两个列表首尾相接来维持顺序，一旦可参与合成的 L1 与冻结的 L2 交错出现，这个隐含顺序就不成立了。
- 落点：`_loadClosedSegments` 给 `ClosedSummary` 带上"可否参与合成 L2"的信息（或者等价地由 `level` 判断）；`CompactionSegment` 增加 `rollable`（可由 `summary && level == 1` 推出）；`_resolveSummaries` 里"直接复用已有摘要文本"的那条路径不变（`reuse != null` ⇒ 查库取文本，绝不重新压原文），收拢循环改为在**上面那张单一有序表**上按"连续的可调整 L1"成组。

### D4 什么时候压：两层同一条规则 —— 攒够阈值就压

**规则（用户 2026-08-29 定下、2026-09-13 重申）**：从最旧开始累加，**一旦累计超过阈值，就把这一批整体压一次成上一级摘要**。这一条**同时管两层**：

- **原文 → L1 摘要**：累加的是原文的估算 token。超过阈值 ⇒ 这一批原文压成一条 L1 摘要。**不等窗口装满** —— 我第一版把"只有装不下才压"当成规则复述，那是读了现状，已更正（见 Context 的第四处偏离）。
- **L1 摘要 → L2 摘要**：累加的是 L1 摘要的实测 token（只算还没被任何 L2 摘要覆盖的那些）。超过阈值 ⇒ 这几个 L1 摘要压成一条 L2 摘要。

**一次压几条（"这一批"到底是哪一段，必须说死）**：**从最旧的、还没被压过的原文开始累加，每累计超过阈值就切出一批；一直切到剩下不足一个阈值为止。** 切出来的每一批各压成一条 L1 摘要；**最后剩下那一截（不足一个阈值）原样发送**。举例：总量是一个阈值的 3.5 倍 ⇒ 切出 3 批（每批约一个阈值）压成 3 条 L1 摘要，剩下半个阈值的原文原样发送。总量刚刚超过一个阈值 ⇒ 切出 1 批（约一个阈值），剩下的原文不足一个阈值。

**⚠️ 这与现有 `_nominalFoldEnd` 的切法不是一回事**（本条为审查发现的第三处问题）：现有做法是"从最新往回保留、直到累计刚好不超过阈值，其余**全部**压缩"，于是当总量刚刚超过阈值时，它压掉的是最旧那一**小截**（不到阈值），留下的原文反而可以到阈值那么多 —— 方向正好相反。改为统一规则后，`_nominalFoldEnd` 的切分方向要跟着改，tasks 必须点名覆盖（见 D7）。

**⚠️ 2026-09-20 执行时又发现一处措辞坑（已改）**：这段原先写成"一直加到**首次**超过阈值为止 —— **那一段**就是'这一批'"，字面照做的话远端永远只有一批（切出来的批数恒为 1），而"批数大于 1"正是"由 AI 挑选批次分界"那套机制唯一的触发条件 ⇒ **那套机制会被悄悄变成永远不执行的死代码**（Non-Goals 里明写"不改这套机制"，自相矛盾）。正确读法就是上面改后的写法：**反复按同一个规则切**，所以多批仍然存在、那套机制仍然会被调用。

**模型容量（预算）在这套规则里剩下什么作用**：只决定**兜底** —— 按上面的规则压完、合并完，如果发出去的内容仍然超过模型容量，就把最旧的那部分**这次不发**（磁盘上的数据不删）。**它不再是"要不要开始压"的开关。** 直接结果是：将来会出现"窗口远没装满、但已经有摘要了"的情形，这是规则的应有之义。

**落点**：判断"要不要跑这一趟"的入口 —— `CompactionEngine._foldTail` 里那条 `totalProxy <= budget` 早退、`buildTree` 的 `shouldCompact`、`lib/main.dart` 里后台压缩的早退判据 —— 都要改成认这两条阈值触发。已落盘 L1 的实测 token 随节点存着（`ClosedSummary.tokenCost`），纯函数层就能判断攒够了没有；本轮新产出的 L1 摘要要等实测之后才能判断，由收拢循环承担。

**收拢循环的终止性（审查发现，必须写成规则）**：继续条件从"还超容量"扩为"**还超容量 或者 尚未被拒的可压累计仍超过阈值**"时，**合成被拒**（合成出来的 L2 摘要实测不小于被替换的那几条 L1 之和）那条路径现有实现是"带 `total > budget` 条件的排空" —— 在"因超阈值而进入、但投影并没超容量"的情形下它会**一步都不删、原样再来一遍**，于是同一组被反复送进 `summarizeText`，既不终止也不符合"每次合成只调一次"。规则定死：**被拒的那一组必须记下来（本次已试），继续条件只看尚未被拒的条目**；未超容量时被拒即不再重试。判据见 D7 与 tasks。

**代价（如实记）**：压缩会比现在**早得多**地发生（窗口只用了一部分就开始压），细节**不可逆地变粗**，发出去的原文最多只剩最近不到阈值那么多。这是规则的直接结果，不是我的实现取舍；嫌压得太早或太狠，就调那个百分比（D8 的表给了频率量级）。

### D5 摘要能写多长，不再由本设计指定

`sidecar/src/model_gateway.cpp` 的摘要请求不再写死 `max_tokens = 1024`（改用模型/接口自己的默认值；`Docs/DeepSeekAPIDoc.md` 记载：`max_tokens` 取值 1 到 384K，**非思考模式默认 8K**）。`thinking.type = "disabled"` **必须保留** —— DeepSeek 的 `/v1/messages` 默认开启思考（`Docs/DeepSeekAPIDoc.md` §2.7.1 注），去掉它会让摘要把额度烧在推理上（这一条源码注释里已有记载）。"摘要一定更小"这个保证**只**由实测判据承担，不再依赖一个写死的数字。

**连带的两处同步修改（审查发现，必须一起做）**：①`openspec/specs/model-gateway/spec.md` 里"摘要 profile 的 `max_tokens` SHALL be 512-1024"以及它的场景仍是**生效规范**，本变更必须补一份 `specs/model-gateway/spec.md` 的 MODIFIED（否则实现改完就与一条未被修改的规范冲突，而 `openspec validate --strict` 抓不到）；②`sidecar/test/http_client_test.cpp` 的 `REQUIRE(body["max_tokens"] == 1024)` 会因此变红，**必须由任务认领**（改它时保留 `thinking.type == "disabled"` 与 `!output_config` 两条断言）。另外：**"不传 `max_tokens` 会落到 8K 默认"这句只在 `Docs/DeepSeekAPIDoc.md` 的 chat/completions 字段表里有记载，`/v1/messages` 端点没有明文** —— 所以新断言只能写成"不再等于设计常量（或该键不存在）"，**不得**写成"等于 8000/8192"（那会引入未核实的外部事实）。

### D6 配置向后兼容，不加界面（2026-09-13 已拍板）

配置里没有这项就用缺省 25（**缺省值 25 已于 2026-09-13 拍板确认**）；已有的 `config.json` 不需要改；`setup_dialog` 不加输入框（`maxContextTokens` 是必填且已有引导，百分比属于可选调优项 —— **用户已拍板"先不加界面"**，只放配置文件 `~/.aliasagent/config.json`）。配置解析测试覆盖"有值 / 没有 / 值非法"三种。

### D7 测试放在哪一层，以及"含 L2"的验收判据

- **单元测试**（`test/unit/compaction_engine_test.dart`）：阈值按比例算出、模型容量翻倍则阈值翻倍、缺省与非法值回落；`l2GroupCount` 没到阈值返回 0（改之前返回条数本身）；删掉写死的 `1025` 下限之后的**行为证据**（一条在旧下限下必被拒的接缝，现在被接受）。

### D8 阈值够不够得着：把账算清楚（不是"已知限制"）

**每次压缩能往"待合成的 L1 摘要"里加多少**：一次压缩会把"最新保留原文"之外的那一截（大约占模型容量的 1 − 百分比）切成若干批，每批累计到阈值大小就压成一条 L1 摘要。于是**每压缩一次，待合成的摘要总量增加约「(1 − 百分比) ÷ 百分比 × 每条摘要的大小」**。

**用具体数字看**（模型容量 100 万 token、每条 L1 摘要约 1000 token）：

| 配置的百分比 | 阈值（要攒够多少摘要 token） | 每次压缩大约增加多少 | 大概压缩掉多少原文才出现第一条 L2 |
|---|---|---|---|
| 25% | 25 万 | 约 3000 | 约 6000 万 token 的对话 |
| 10% | 10 万 | 约 9000 | 约 1000 万 token 的对话 |
| 5% | 5 万 | 约 1.9 万 | 约 200 万 token 的对话 |

**这张表怎么读（审查后重写：第一版把它判成"取值问题、不是实现缺陷"，那是被明令禁止的收口方式）**：

- 表里"每次压缩大约增加多少"用的是**每条 L1 摘要约 1000 token** 的假设。**这个数不是固定的**：D5 之后摘要长度由模型决定（`Docs/DeepSeekAPIDoc.md`：`max_tokens` 取值上限 384K、非思考模式默认 8K），而本仓库实测的 L1 是 610 / 626 token。**要凑够阈值，需要同时存在的 L1 条数 = 阈值 ÷ 每条摘要大小** —— 按 1000 算约 250 条，按模型默认上限 8K 算约 31 条。
- 所以"够不够得着"取决于三件事：**阈值本身、每条摘要能有多大、能同时攒多少条**。第一版只算了第一件，就下结论说"这是 25% 的算术后果、不是实现缺陷" —— 那正是用户钉死的自检第 5 问**明令禁止**的写法（"够不着 ⇒ 是实现缺陷，必须修，不许写成'已知限制/病理情况'收口"）。**现更正为**：
  - **实现侧的三重封顶**（落盘即冻结 / 条数门槛 / 写死常量）**必须修** —— 本变更已修（D2 / D3 / D5）。
  - **第四重封顶**（每会话 30 条上限 + 500000 token 上限）**已决定删除**（见 D9）—— 它不只是偏离要求，本身还是烂设计（量错了对象 + 触发后永久停摆）。
  - 把封顶都去掉之后，剩下的才是**取值问题**：在"100 万窗口 + 25%"下，L2 需要单个会话积累到「阈值 ÷ 每条摘要大小」条 L1，按实测摘要大小约 600 token 算，那是**千万量级 token 的对话**。这不该被称为"病理情况"，但它确实是**阈值取值本身**决定的。**2026-09-13 用户已拍板：就取 25% 先落地，跑完真实模型用例后拿实测数字再调**（缺省百分比是本变更唯一的旋钮）。若哪天要求"任何会话长度下都必然出现 L2"，那与"阈值 = 窗口 × 百分比"这条规则本身冲突，届时要改的是规则、不是实现。

### D9 每会话压缩上限（30 条 / 500000 token）**决定：两条都删**

现状：`kMaxFoldsPerSession = 30` 与 `kMaxFoldTokensPerSession = 500000`，判据 `isFoldBudgetExceeded`。**它是烂设计，用户 2026-09-13 当场斥之，本变更直接删掉，不再作为待议项。**

**来源（必须写清，免得以后又被当成"用户要求"）**：**这是我自己加的，不是用户要求。** 它出自上一个变更 `2026-09-01-add-auto-context-compaction` 里我写的 D10「便宜层优先 + 压卷预算」，那句"每会话压卷次数/token 上限"在归档 design 里**没有任何用户指示支撑**；用户在那条链上的要求始终只有"阈值怎么算、什么时候压"。**它跟用户的要求既不同源、也不同向，而且反过来把用户要求的行为掐死了。** 烂在三处：

1. **量错了对象**：它数的不是"这个会话花了多少"，而是"**已经产出过多少条摘要**"（`summary_nodes` 里 `level >= 1` 的行数；被粗摘要覆盖掉的那些小摘要行**从不删除**，所以这个计数只增不减）。它把"已经做完的有用工作"当成了"要防的开销"。
2. **触发后的后果比它要防的事更糟**：越过一次就**永久关闭压缩**（内联与后台两条路一起停，之后每轮整段原文发送）。它防的是"摘要调用花太多钱"，实际造成的却是"这个会话再也不压缩了" —— 而那正是压缩存在的理由。它不是降级，是**停摆**，而且**关上就不会再开**。
3. **阈值本身也是被禁的那两类**：30 是条数门槛、500000 是与窗口无关的写死绝对数（撞用户 R1 / R3）；而且它比阈值先咬合 ⇒ 本变更承诺的"够得着"根本立不住。

**决定（用户 2026-09-13：「对于这种狗屎设计，没有任何留着的理由」）：整套删干净** —— 两条常量、两个 getter、`isFoldBudgetExceeded`、`_foldBudgetExceeded`（含它上方那段描述动机的文档注释）、`_callModel` 与后台压缩里的**两处早退**（前者删掉后把原 `else` 分支拉平成顺序执行）、以及**把它钉成预期行为的那个用例**（`cost_discipline_test.dart` 的 `5.1 fold budget cap`；删它属于修改验收标准，**已获用户明确授权**）、还有活文档里描述这道上限的表述（`Docs/context-compression-reference.md`）。同文件里 `5.2 break-even` **不属于这道闸门**（它测的是"压缩确实省"这个独立性质），**已拍板保留**（2026-09-13），只清掉与已删设计相关的命名与注释。归档目录不改。任务见 tasks 第 5 组（5.1 代码 / 5.2 用例 / 5.3 文档 / 5.4 意图收口）。

**代价（如实说）**：极长会话的摘要调用成本会随对话长度增长（每压出一批新摘要就要调一次模型）。这是"长会话仍然可用"必须付的钱，不再是靠关掉功能来省。**2026-09-13 已拍板：先不补替代护栏** —— 也就是说"成本不能失控"这个意图**暂时无人承担**，文档里如实这么写，不许假装它还在（tasks 5.4）。

**将来若要再加成本护栏，必须同时满足三条**（否则就是同一个烂设计换个马甲 —— 已记入 `Docs/rejected-approaches.md` 第 22 条）：
① **量的单位就是被保护的资源**（token / 花费本身），不是"做了多少次""存了多少条"这类单调增长的计数；
② **阈值由模型容量派生**（用户 R2 / R3），不是写死的绝对数；
③ 触发后**降级**（少压一点、压得更粗、跳过某些可压内容）而不是**停摆**，并且**能恢复**。

## Risks / Trade-offs

- **[25% 在 100 万容量下 L2 摘要极罕见]** → D8 已把账列成表；百分比可配置、可实测调整；集成测试在小容量下证明通路成立。
- **[百分比从 50 降到 25 会缩小"最新对话保留原文"的那一块]** → 如实记录（D1）；这是取值副作用；若实测发现最近的上下文不够，调百分比，或将来把两个用途拆成两个**都是容量百分比**的旋钮。
- **[每会话压缩上限会先把路堵死]** → 见 D9：**已决定删除**（两条常量、两个 getter、判据函数与两处早退一并去掉，既有用例同步改写）。
- **[攒够阈值就压 ⇒ 压缩比现在早得多地发生，即使窗口还有大片空余]** → 用户 2026-08-29 定的统一规则、2026-09-13 重申（D4），不是实现取舍；代价是细节更早不可逆地变粗、发出去的原文最多只剩最近不到阈值那么多；嫌太早或太狠就调百分比（D8 的表给出频率量级）。
- **[不再冻结 L1 ⇒ 可能多出摘要调用]** → 合成发生在 L1 摘要累计超过阈值时（不再等超预算）；且"实测变小"才采纳，拒绝后走"最旧的不进本次请求"；每次合成只调一次 `summarizeText`；复用路径不调模型。
- **[既有测试里按"容量除以 2"手算的期望会失效]** → 属预期；**2026-09-13 用户已授权更新那三处期望值**（算批次的单元测试、检查发给模型内容的集成测试、C++ 里的摘要长度断言）；**只改与实现细节绑定的期望值，不得放宽或删除断言**；规范侧已同步改成百分比表述。
- **[归档时 MODIFIED 块落不到基线规范上]** → 基线的小节头是旧格式 `## ADDED Requirements`，openspec 只在 `## Requirements` 下收集条文；补齐之后还要求有 `## Purpose` 小节（实测第二次失败报 `Spec must have a Purpose section`）。**本变更要改的两份基线（`context-compaction`、`model-gateway`）都改**；其余 **36 份**另开一单（tasks 1.1）。
- **[改成单一有序表可能打乱顺序]** → 专门加"覆盖范围严格递增"的断言（D7 第 3 条）。
- **[C++ 与 Dart 不同步 ⇒ 出现 `Failed to lookup symbol` 这类假回归]** → 走项目自己的入口 `run.bat`，或 `scripts\sync_sidecar_dll.ps1`；`test/unit/sidecar_dll_freshness_test.dart` 已是守卫。
- **[数据安全]** → 不删任何行；L2 摘要是**新增**行；`materialize` 的覆盖键含 `level`（已实现）；被合成掉的 L1 节点保持原样。
