## Context

**压缩今天什么时候跑，用户看得到什么**（下面两条路径都以 `lib/main.dart` 里的 `_resolveSummaries` 为唯一实现）：

```
你按发送 ─▶ 载入已落盘摘要 ─▶ 挑分段主题 ─▶ 算计划 ─▶ 逐段生成摘要 ─▶ 才把请求发给模型 ─▶ 第一个字
                （数据库）      （模型请求）   （纯计算）   （模型请求，可能多次）        ↑ 这之前界面一动不动

你空闲 2 秒 ─▶ 同一套流程（后台压缩）  ─▶ 落盘 ─▶ 结束      ↑ 今天完全不可见，你一发消息它就中断让路
```

实测量级（2026-09-27 那次展示运行）：单次模型请求 3–6 秒，连续 14 次共约 66 秒；那次压出 9 条一级摘要、3 条二级摘要。

**今天界面上已有的相关状态**

| 状态 | 在哪里 | 能不能当"正在压缩"用 |
|---|---|---|
| 发送中标志 `_isStreaming` | `ChatScreenState`，发送时置位 | 不能：没触发压缩的普通发送它也是开的 |
| 后台折叠标志 `_foldInFlight` | `ChatScreenState`，只覆盖后台那条路径 | 不能：漏掉发送前那条路径；且它在 `finally` 里改完不重画界面 |
| 上下文快照 `_contextSnapshot` | 每次真正发送前捕获，只增不改 | 只说明"上一次发出的是什么"，不说明正在做什么 |

**约束（用户已钉死，本变更不得触碰）**：压缩的触发只由"模型上下文总量 × 百分比"这一个阈值决定，不许引入条数门槛或绝对 token 数；数据永不删除；摘要只在实测比被它替换的内容更小时才被接受；最多两级；投影里每一段只用一种表示。

## Goals / Non-Goals

**Goals**

- 压缩期间，**对话视图**（输入框上方）与**真实上下文视图**（这一屏顶部）都能看到一条状态提示。
- 提示说清"正在做什么"（挑选分段 / 生成一级摘要 / 合成二级摘要）与进度；总数已知时给"第 k 段，共 n 段"，未知时只给已完成数。
- 提示只在确实有压缩在进行时出现，并在四种结束情形下都消失：成功、失败、异常、被用户的下一次发送打断。
- 没有任何压缩在进行时，这个组件不渲染内容、不占据布局空间，既有界面布局与截图基线不变。
- 状态对测试可读（与既有的"上下文快照"一样，从 `ChatScreenState` 上读），能写出"压缩期间它必须非空闲、结束后必须空闲"的断言。
- （2026-10-02 追加）**"这一轮要不要为压缩等待"由等待门槛单独决定**：不压就发的话这一趟占模型总上下文的比例超过配置的百分比（缺省 75）才等；不到就不等、不产生任何摘要调用。

**Non-Goals**

- 不改压缩的触发时机、阈值算法、投影分档规则、摘要的合成与接受条件 —— 本次只让已经在跑的过程可见；追加的等待门槛也只决定"这一轮是否等它完成"，不决定"什么时候压"。
- 不把等待门槛做成绝对 token 数、条数或计时器（用户钉死的硬约束：只允许"模型总上下文 × 百分比"）。
- 不显示压缩中尚未发出的摘要正文（真实上下文视图按定义只显示"真正发出去的那一份"）。
- 不加取消按钮、不做压缩历史面板、不在侧边栏标记其它会话的压缩。
- 不给"等待模型第一个字"那段空窗加提示（同一个毛病、但不是压缩；另开变更）。

## Decisions

### 决定 1：状态由真正做压缩的代码置位，不从别的标志推断

候选与取舍：

- **A. 从发送中标志推断** —— 否。没有触发压缩的发送它也是开的，提示会变成"每次发送都在压缩"，是假的。
- **B. 直接拿后台折叠标志当界面状态** —— 否。只覆盖后台那条路径，发送前那条漏掉；而且它结束时在 `finally` 里改完不重画，界面会永远停在"压缩中"。
- **C. 选定**：新增一个状态值，由发起压缩相关模型请求的地方置位，两条路径共用同一处清除。

### 决定 2：什么时候该亮 —— 用"确实有内容要压"这个判断当闸门

后台压缩在你空闲 2 秒后启动，而它经常发现"没到阈值、无事可做"就返回；如果提示挂在"尝试压缩"这一步，每次发送都会闪一下。

闸门用现成的纯函数：`CompactionEngine.resolveFoldSeamInputs` 返回非空，等价于"这次确实有远端内容要压"（它和算计划的 `_foldEndFor` 共用同一个判断，两者不可能不一致；返回空就说明没跨过阈值、无事可做）。

于是：

- **挑选分段主题**这一步：只在 `resolveFoldSeamInputs` 非空、确实要去挑的时候才亮（这时它自己会发一次模型请求，几秒）。
- **逐段生成 / 合成摘要**这一步：进入 `_resolveSummaries` 就亮；缓存命中的段不产生模型请求，进度会跳跃（见风险 3），不额外做平滑。
- 没配分段选择器时，挑选那一步不亮，直接从"逐段生成"开始 —— 仍然不闪，因为那时已经确定有内容要压。

### 决定 3：提示说什么

- 阶段名 + 进度：`正在压缩较早的对话：生成第 3 段摘要，共 9 段` / `正在把一级摘要合成二级摘要：第 2 段，共 3 段` / `正在挑选分段主题`。
- 后台压缩时补一句：`你发消息会让压缩先让路`（这是既有行为：用户发送会打断后台压缩）。发送前那次压缩不显示这句 —— 那时用户本来就在等。
- 不加百分比、不加预估剩余时间：两者的真实数据都不存在。

### 决定 4：两个视图各自放在哪、写什么

- **对话视图**：固定在输入框上方（不随消息列表滚动）。压缩期间用户正等在这里，这是对话视图今天唯一能显示"正在忙"的地方 —— 现在从按下发送到模型吐出第一个字，整段界面毫无变化。
- **真实上下文视图**：固定在这一屏顶部（不随内容滚动）。提示里必须写明：**下面显示的是上一次实际发出的内容，压缩结果要等下一次发送才出现** —— 这一屏按定义只显示真正发出去的那一份，压缩期间它不会变，不写这句用户会以为它在刷新。
- 两个视图共用同一个组件与同一份状态，只在措辞上多一句附注，避免两处各写一遍、日后改一处漏一处。
- **还没有任何快照时**（应用启动后还没发过消息、这一屏显示占位文字）：提示与占位并存，措辞不变。

### 决定 5：生命周期与清除

- 状态由 `ChatScreenState` 单点持有，只读 getter 供测试读取。
- 两条路径（发送前、后台）都走同一处清除：`finally` 里清空，**并且这一次清除必须触发界面重画** —— `_foldInFlight` 今天就是漏了这一步，别再犯。
- 状态对象只在置位和进度更新时重建，空闲态是一个常量，不分配。

### 决定 6：空闲不占位

空闲时组件返回 `SizedBox.shrink()`，不留空白高度、不加分隔线，既有布局与截图基线保持不变。

### 决定 7（2026-10-02 追加）：等待判据的分子 = "不压就发"的那一趟估算总量

用户说的是"现有发送给模型的原文 + 一级 + 二级摘要"。落到可算的量：**按当前库里已有的摘要拼出来的那一趟**会发出去的总估算 token（会以摘要形式发的按它落盘时的实测 token 计，其余按原文估算计），除以 `maxContextTokens`。

- 发送前拿不到模型回报的 usage，只能用本地确定性估算器（与算阈值用的是同一个），这也保证判据可复现、不发任何请求。
- 备选（否）：拿"原文总量"当分子 —— 那等于把等待门槛又绑回压缩阈值（原文涨过 25% 就等），与用户要求相反。
- 备选（否）：拿"压完之后预计能降到多少"当分子 —— 那要假设压缩比，是规范明令禁止的。

### 决定 8（追加）：等待阈值与配置键

等待上界 = `maxContextTokens × compaction_wait_threshold_percent ÷ 100`，缺省百分比 **75**。校验规则与既有 `compaction_threshold_percent` 完全一致（1..100 的整数；写 `0`、负数、大于 `100`、小数、字符串都按没写处理，按 75 走，并在日志里打印一行提示）。同样禁止绝对 token 数与条数门槛。

### 决定 9（追加）：比例不到时怎么拼投影 —— 一个摘要调用都不许发

新增一条"只取已落盘"的投影路径：计划里**已经落盘、可以直接复用**的段照旧取库；还没压过的段**按原文发**（作为原文段进入投影）。整个过程**不调用摘要器**。落点写死：给 `_resolveSummaries` 的内层函数加一个"只取不生成"的开关（复用它的 closed 分支与取文本逻辑 —— 已落盘摘要的正文读取与"缺节点就报错"这两段只存在于那里，另写一份必然分叉），关掉后所有还没落盘的段按原文进投影。

**分叉点必须在那一步之前**：判断"等 / 不等"要放在 `_prepareSeamChooser` **之前**。生产中分段选择器是真家伙（`ModelSeamSelector`），放在它后面时，比例不到的这一轮照样会发一次"挑选分段主题"的模型请求、并（冷缓存时）把提示亮起来 —— 那就等于没做到"不等"，而只看"假摘要器零调用"的用例查不出这件事（用例里没注入分段选择器）。

- 备选（否）：照旧生成摘要但不等待（后台跑完再替换）—— 那会同时出现"这一段既发原文、又正在压"，而且"这一轮不等"变得不可证（摘要器被调用了，只是没等），用户要的"不等"就没有干净的判据。
- 判据要能失败：测试里用一个计数假摘要器，断言这一轮它被调用 **0 次**；另用一条"注入了分段选择器"的用例断言这一轮连分段选择请求都没发（否则上面那条产线漏洞没人守）。

### 决定 10（追加）：不许死等的两条出口

1. 压完仍超过**等待上界**但没超过 `maxContextTokens` ⇒ **照发**，什么都不丢（等待上界只决定"这一轮等不等"，它不是省略的门槛 —— 既有省略只在投影超过模型容量时才发生）。
2. 压完仍超过 `maxContextTokens`，或摘要生成失败 / 抛异常 ⇒ 沿用既有的两条降级：把最旧的可省略内容留出这一轮投影（数据留在磁盘）、退回原样发全文。

### 决定 11（追加）：提示语义不变

"正在压缩"提示只在真的有压缩在跑时出现。新规则下：发送前那次只有**真的在等**（比例超过等待上界）时才会跑，所以提示也只在那种时候出现；比例不到时发送前不压，压缩发生在空闲后台那一趟，提示那时照旧出现（含"你发消息会让压缩先让路"）。两个视图的呈现一个字不改。

### 决定 12（追加）：状态要带归属，不许谁先结束谁清

审查发现（对抗验证那一轮）：压缩状态是一个没有归属的字段，而"后台折叠"与"发送前压缩"可能同时在跑 —— 用户发送会抢占后台那趟（它随后抛异常、走 finally），如果它恰好落在发送前那趟置位之后收尾，就会把发送前那趟正在显示的提示清掉；反过来也一样。另外切换会话既不销毁界面也不清状态，旧会话的压缩提示会挂在新会话界面上，直到那趟自己结束。

所以：状态要带一个归属标记（哪条路径置的、属于哪个会话），清除时只在归属匹配时才清；切换会话时把不属于当前会话的状态清掉。判据要能失败：构造"后台那趟被抢占后收尾"与"发送前那趟正在跑"同时存在的那一刻，断言提示仍在；以及"发送后切到另一个会话"时，断言新会话界面上找不到提示。这两条现在都不存在（现有抢占用例里用户那趟根本没触发压缩）。

## Risks / Trade-offs

- **进度会跳跃（缓存命中）** → 接受。缓存命中的段不发模型请求，进度可能从 2/9 直接到 9/9；不做平滑、不伪造中间值，因为"正在生成第几段"本来就是真实的。
- **总数不一定事先知道（合成二级摘要那一步）** → 那一步只显示"正在生成第几段"，不写"共几段"（不编造分母）。规范里已按此措辞（总数已知才给"共 n 段"）。
- **后台压缩的提示可能让用户以为必须等** → 提示里写明"你发消息会让压缩先让路"。
- **2 秒防抖期内不显示** → 正确：那时还没开始做，只是排了个队。
- **清除时界面可能已经销毁**（压缩期间切换会话/关闭窗口） → 清除要带 `mounted` 判断，否则 `setState` 会抛异常。
- **提示与"发送前压缩"重叠期间的语义** → 发送前压缩期间对话视图同时存在"你的消息已上屏"和"正在压缩"；这是真实情况（消息已存库、请求还没发），不额外解释。
- **live 截图的时间窗** → 真实压缩窗口只有几十秒，可能抓不到；稳定截图靠假摘要提供者卡住状态（widget / 集成层），live 层用轮询等到状态非空闲再截图，抓不到就如实记为未截到，不算通过。
- **（追加）连续快速发消息会推迟压缩** → 一直不空闲 ⇒ 后台折叠没机会跑 ⇒ 投影一路涨到等待上界才压，那一次的等待会比现在长（一次压一大批）。这是本设计换来的代价，要写进 `Docs/user-guide/context-compaction.md` 让用户知道；兜底是"比例一到就压"且"压完仍超比例时省略最旧"，不会失控。
- **（追加）等待判据是估算** → 与阈值用同一个估算器，误差同源；不追求与模型回报的 usage 完全一致（发送前不可能拿到）。
- **（追加）后台折叠成为主力入口** → 它已经是被测试钉住的行为（空闲触发、用户发送让路、事务落盘），本次不改它；风险是"用户从不空闲"这一情形，由等待上界兜住。
- **（追加）不改等待门槛时不许偷偷压** → 判据要能失败：计数假摘要器在"不等"的那一轮必须被调用 0 次；把它改成"照样生成但不等待"，这条断言必须红。

## Migration Plan

- 不涉及数据库、配置、接口迁移：只新增界面元素、一个界面状态、一个配置键。
- 空闲时不占位，所以**不需要**更新既有截图基线；若冒烟里的视觉回归出现新增失败，那就是本变更改变了布局，要修的是本变更。
- （追加）缺省值生效后**行为会变**：原本每轮都可能等压缩，现在比例不到就不等。回滚 = 把 `compaction_wait_threshold_percent` 调到 25（等于回到"攒过阈值就等"）或还原本次提交。既有配置没有这个键，按缺省 75 走，用户不需要改任何东西。

## Open Questions

- 是否也给"等待模型第一个字"那段空窗加一条状态（今天同样什么都不显示，压缩只是把它拉长）—— 本次列为 Non-Goal，需要时另开变更。
- 是否要在侧边栏给"正在压缩的其它会话"加标记 —— 本次不做。
- （追加）缺省 75 是用户给的"比如"，先按 75 落地；若实测偏晚（等待那一次太长）就调小，改一个配置值即可。
- （追加）是否在界面上显示"当前占比离等待门槛还有多少"—— 本次不做。
