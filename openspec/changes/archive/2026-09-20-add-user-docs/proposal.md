## Why

这个工程现在**只有一份 `README.md`**（环境要求 / 构建运行 / 配置 / 测试 / 目录结构），**一份面向用户的功能使用文档都没有**，README 里也没有功能索引。结果是：拿到这个应用的人（不懂本仓库内部结构、也不打算读代码）不知道它能做什么、每个功能怎么用、出错时看到的现象是什么意思 —— 例如"为什么 `read_file` 说路径越界""摘要标记是什么""搜索为什么没结果""配置里到底能写哪些键"。

`CLAUDE.md` 里已经立了规矩（面向用户的文档必须与功能同步：README 当总入口 + 每个功能一份使用说明，改动功能必须同步改文档），但**这份文档本身还不存在**。本变更就是把这个缺口补上，并且**加一条能失败的校验**，让"文档漏了、索引漏了、文档里写的键在代码里不存在"这三类腐烂当场被抓住。

## What Changes

- **补一整套面向用户的功能使用文档**：`Docs/user-guide/` 下每个面向用户的功能一份，写"怎么用"（在哪、怎么操作、参数怎么填、出错时会看到什么、有哪些限制），**不写内部实现**。
  按代码里实际存在的功能，需要这些（共 8 份）：`chat.md`（对话与流式回复、工具调用卡片、思考卡片、会话管理）、`real-context-view.md`（「真实上下文」视图）、`context-compaction.md`（上下文压缩：什么时候压、摘要标记怎么看、百分比怎么调、原文去哪了）、`tools-file.md`（`read_file` / `write_file` / `list_dir` / `glob_file` / `grep_file`，含**工作区边界**）、`tools-web.md`（`web_search` / `web_fetch`）、`tools-browser.md`（`browser_navigate` / `browser_click` / `browser_type` / `browser_snapshot` / `browser_available`）、`configuration.md`（配置文件各键、首次启动的设置对话框、每个 agent 类型能配什么）、`troubleshooting.md`（常见现象与去哪看日志）。
- **`README.md` 增加"功能文档索引"一节**：一句话说清每个功能是什么、链接到对应的使用文档；并补上"工作区 = 用户主目录"这类**最容易踩的前提**。
- **加一条能失败的一致性校验**（`test/unit/user_docs_test.dart`）：
  1. `Docs/user-guide/` 下每份文档都在 README 的索引里被链接到；反过来，索引里链的每个文件都真实存在（**双向一致**）；
  2. 文档里写到的**配置键**，在产品代码的解析路径里确实存在；
  3. 文档里写到的**工具名**，在代码注册的工具清单里确实存在。
  这样"新增功能忘写文档""文档写了个不存在的键""索引与文件对不上"都会直接变红。

## Capabilities

### New Capabilities

- `user-documentation`：面向用户的文档（README 总入口 + 每个功能一份使用说明）必须存在、必须互相索引一致、且其中写的配置键与工具名必须能在产品代码里核对到。

### Modified Capabilities

（无 —— 本变更不改任何产品行为，只补文档并加一条文档一致性校验。）

## Impact

- **文档**：新增 `Docs/user-guide/` 目录及其中 8 份文档；修改 `README.md`（加功能索引、补工作区前提）。
- **测试**：新增 `test/unit/user_docs_test.dart`（纯文件读取与文本比对，不开窗口、不连网络）。
- **代码**：**不改任何产品代码**（`lib/`、`sidecar/`、`scripts/` 一行不动）。文档内容全部照**当下代码的真实行为**写，不写"打算怎么做"。
- **风险与边界**：文档里的界面文案 / 配置键 / 工具名一旦与代码脱节，那条校验会红 —— 这正是它的用途；但它只能查"名字对不对得上"，查不了"说明写得准不准"，后者靠人来读。
