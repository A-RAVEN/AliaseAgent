## Context

**现状（2026-09-20 读代码与实测核实，指针写名字不写行号）**：

- `scripts/browser_worker.py` 的 `_handle_click` 里，跟随新标签页的做法是：在 `context.expect_page(timeout=NEW_PAGE_WAIT_SEC * 1000)` 这个块里点击；`NEW_PAGE_WAIT_SEC = 1.0`（只有 1 秒）。块正常退出说明新页开了 ⇒ 跟随；块以超时退出 ⇒ 当作"这次是原地跳转"，继续用原页面。
- **实测的失败**：`test/integration/browser_worker_test.dart` 的 `browser_worker: click a target=_blank link FOLLOWS the new tab (design 甲)`，**单独跑必过**；跟着**全量** `flutter test` 跑约**一半概率**失败（现场：点击后 URL 与快照都停在被点的原页面）。全量时机器负载高，弹窗注册得比 1 秒更晚。
- **正确性已核实的一点**：Playwright 同步 API 的 `EventInfo.value` 是 `while not self._future.done(): self._sync_base._dispatcher_fiber.switch()` —— 它是**阻塞等待**事件到达，不会提前返回空。所以"读取时机太早"**不是**根因（我一度这么判并改了读取位置，那是等价于没改的改动，已撤回）。**根因是等待窗口太短。**
- **不确定的一点（本设计必须诚实标出）**：文件里的注释写着"轮询 `context.pages` 在事件循环中途看不到新页 —— 弹窗事件只有在 Playwright 的 API 泵动时才冲洗出来"。这句话是**先前写下的判断，本轮没有独立核实过**。它直接影响"超时后再补看一眼页面集合"这个候选做法**能不能用**。

**约束**：worker 是长期存活的进程，点击是高频操作 —— **不能为了稳妥让每一次普通点击都多等几秒**；模型可见的返回内容（stdout 的 JSON）不得新增字段；worker 与 sidecar 之间的报文格式不变。

## Goals / Non-Goals

**Goals:**

1. 点击**确实会开新标签页**的元素时，新页即使晚于 1 秒才出现，也要被跟随（AI 读到的必须是真正的落地页）。
2. 普通点击（原地跳转）**不多等**：日常点击的耗时与现在一致。
3. "该开新页却没等到"这件事**可观测**，不静默。
4. 有一条**确定性**的复现用例：不依赖机器忙不忙，在改动前的代码上**稳定失败**，改完**稳定通过**。

**Non-Goals:**

- 不动 `ctest` 里那条联网搜索用例的不稳定（另一件事，另行立项）。
- 不改"窗口隐藏 / 最小化 / 被遮挡"相关的任何行为。
- 不改多标签页管理方式：新页照旧被跟随、原页照旧保留、会话关闭仍是兜底。
- 不新增任何对模型可见的字段或计数。

## Decisions

### D1 点击前先判断"这个元素会不会开新标签页"

用一次 DOM 读取取到目标元素的 `target` 属性（`target="_blank"`，或等价的 `_new` / 具名目标）。判断结果是**布尔值**，只决定"这次点击该用长窗口还是短窗口"。

**为什么不用"看得更细"的判断**（例如解析 `onclick` 里有没有 `window.open`）：字符串匹配点击处理器太脆（拼接、包装、事件委托都会绕过它）。**代价如实记**：用 JS 处理器开新页、而锚点本身没有 `target` 的点击，会被判成"短窗口"那一类 —— 这一类的兜底见 D3。

### D2 判定"会开新页"时，这一次点击用更长的有界窗口

`target="_blank"` 的点击用 `NEW_TAB_WAIT_SEC = 5`（秒）；其余点击继续用 `NEW_PAGE_WAIT_SEC = 1`。两个窗口都是**上界**：新页一到就立即返回，不会白等。

**备选与否决理由**：

- **把全局窗口直接调到 5 秒** —— **否**。注释里写明：没有弹窗时 `expect_page` 会把整个窗口**等满**。全局调到 5 秒，等于**每一次普通点击都多等 4 秒**，代价落在最高频的操作上。
- **不再依赖等待窗口，改成"点完之后循环看页面集合"** —— **暂不作为主做法**。它依赖上面标为"不确定"的那句注释（中途轮询能不能看到新页）。它作为 D3 的补看保留；如果实测证明它可靠，将来可以再简化删除 D2 的长窗口。

### D3 无论走哪个窗口，超时后再补看一眼"页面集合是否多出一个"

点击**之前**记下 `context.pages` 的集合；超时之后再取一次，多出来的页就是新开的那一个。这一步很便宜（一次集合比较），而且**不会误判**：多出来的页肯定是这次点击或它的异步处理器开的。

**为什么保留它**：它覆盖 D1 漏判的那一类（锚点没有 `target`、由 JS 开新页）。**不做**成"无限轮询"——它只在超时之后看一眼，不额外等待。

### D4 "该开新页却没等到"要记一笔

当 D1 判成"会开新页"、但两个窗口加上补看都没找到新页时，往既有的记录通道（stderr 的 `browser-record:`）里记一条，说明"这次点击判定会开新页、但没等到"。**为什么不改成模型可见的报错**：这不是失败（可能用户自己也拦了弹窗、或页面自己取消了默认行为），把它变成报错会污染模型看到的内容；记在记录通道里，测试与排查能看见。

### D5 判据：确定性复现，不靠"机器忙不忙"

测试页里放一个链接：`target="_blank"` + 点击处理器里 `preventDefault()` + `setTimeout(() => window.open('/landing'), 1500)` —— 新标签页**必然在 1 秒窗口之后**才开。

- **改动前**：1 秒窗口错过它 ⇒ 不跟随 ⇒ 快照还是原页面 ⇒ 用例**稳定失败**。
- **改动后**：这次点击被判成"会开新页" ⇒ 用 5 秒窗口 ⇒ 1.5 秒时事件到达 ⇒ 跟随 ⇒ 用例**稳定通过**。

这条替换掉"靠全量套件负载碰运气"的复现方式；既有那条正常时序的用例**保留不动**。

## Risks / Trade-offs

- **[用 JS 开新页、锚点没有 `target` 的点击仍走短窗口]** → D3 的补看兜底；若实测发现这类点击也很常见，再考虑把补看升级为短轮询（届时用同一条确定性用例的变体判据）。
- **[D1 的 DOM 读取可能失败]**（选择器失效、元素被移除）→ 读取失败一律按"不会开新页"处理，走现在的 1 秒路径，**绝不因为判断本身失败而让点击失败**。
- **[`target="_blank"` 但实际不开页的点击，会多等满 5 秒]**（例如处理器里 `preventDefault` 且不开窗）→ 只影响这一类点击；窗口是上界，开了就立即返回。这是本设计换来的确定性所付的代价，如实记。
- **["超时后再看页面集合"可能看不到晚到的弹窗"]**（Context 里那句未核实的注释）→ 这条**只影响 D3 这一层兜底**：D1+D2 的主路径不依赖它，所以即使它无效，主判据（D5 的用例）仍然成立。届时 D3 如实标注为无效，或删掉。
- **[改动会动到浏览器 worker 这个长期存活进程]** → 回滚就是还原这一个文件；不涉及数据、表结构、配置格式。

## Migration Plan

1. 先加 D5 的确定性用例，在**没改 worker** 的代码上跑一遍，贴出它稳定失败的输出（红态先落地）。
2. 再改 `_handle_click`（D1 → D2 → D3 → D4）。
3. 跑该用例 ⇒ 绿；再跑整个 `browser_worker_test.dart` ⇒ 全绿；最后跑一次全量 `flutter test`（会开浏览器窗口，**由主循环自己跑一次**，不派子 agent）。
4. 回滚：还原 `scripts/browser_worker.py` 一个文件即可；那条新用例可以保留（它在旧代码上红，正好是守卫）。

## Open Questions

1. **"超时后再看页面集合"到底能不能看到晚到的弹窗？** 本机装的这个 Playwright 版本里没有核实过。**处置**：不阻塞本变更 —— D5 的用例用的那条路径（D1+D2 的长窗口）不依赖它；跑完那条用例即可判定 D3 这一层是否有效，无效就如实标注或删除。
2. **`NEW_TAB_WAIT_SEC = 5` 这个数够不够？** 它是上界、且只在判定会开新页时生效；实测里弹窗注册约 0.16–0.36 秒、全量负载下更晚。**处置**：先取 5 秒；若那条确定性用例（1.5 秒才开窗）之外还出现更晚的真实情形，再调大这个数，调的依据写进记录。
