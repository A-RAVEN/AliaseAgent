## Context

**现状（2026-09-20 读代码与实测核实；指针写函数名与常量名，不写行号）**：

- `scripts/browser_worker.py` 的 `_handle_click` 里，跟随新标签页的做法是：在 `context.expect_page(timeout=NEW_PAGE_WAIT_SEC * 1000)` 这个块里点击；`NEW_PAGE_WAIT_SEC = 1.0`（只有 1 秒）。块正常退出说明新页开了 ⇒ 跟随；块以超时退出 ⇒ 当作"这次是原地跳转"，继续用原页面。
- **窗口的计时从点击之前就开始了**：`expect_page` 这个块一进入就开始计时，`page.click(...)` 在块内执行。所以"等 1 秒"实际是"点击之前起算的 1 秒"，点击自己耗掉的时间会从等待预算里扣掉。
- **实测的失败**：`test/integration/browser_worker_test.dart` 的 `browser_worker: click a target=_blank link FOLLOWS the new tab (design 甲)`，**单独跑必过**；跟着**全量** `flutter test` 跑约**一半概率**失败（现场：点击后 URL 与快照都停在被点的原页面）。全量时机器负载高，弹窗注册得比 1 秒更晚。归档变更 `2026-09-20-align-compaction-thresholds` 的收尾记录里留着直接证据：连跑 6 次全量，**3 次绿、3 次红**，失败点每次都是同一条。
- **正确性已核实的一点**：Playwright 同步 API 的 `EventInfo.value` 是 `while not self._future.done(): self._sync_base._dispatcher_fiber.switch()` —— 它是**阻塞等待**事件到达，不会提前返回空；超时会抛异常。所以"读取时机太早"**不是**根因，**根因是等待窗口太短**。
- **既有跟随路径的断言口径（五条，不是一条）**：`r['ok']` 为真、快照含 `LANDING`、点击记录 `browser_opened > 0`、`adopted_tabs > 0`、`tabs >= 2`（后三条从 stderr 的 `browser-record:` 行读）。新用例必须按同一口径写。
- **既有计数机制只有计数、没有跟随**：`_install_page_handler` 里注册的 `on_page` 只做 `self._browser_opened += 1`（并且跳过 `page.opener() is None` 的页），真正的跟随只发生在 `_handle_click` 的 `expect_page` 分支（那里 `self._adopted_tabs += 1`）。那个函数的注释写着"跟随是靠点击前后做页面集合差集实现的"，**这句与代码不符** —— 差集根本不存在，实现时顺手把这句注释改对。
- **待修的一个既有注释错误**：`NEW_PAGE_WAIT_SEC` 定义处的注释说 `expect_page` 在没弹窗时会把整个窗口等满；这句话成立，但**没写**计时从点击前开始 —— 这是本次要改的点之一（见 D2）。

**约束**：

- worker 是长期存活的进程，点击是高频操作 —— **不能为了让判据好写就让每一次普通点击都多等几秒**。
- 模型可见的返回内容（stdout 的 JSON）**不得新增字段**；worker 与 sidecar 之间的报文格式不变。
- worker 的命令超时预算：`page.click` 等操作各自上限 30 秒（`OP_TIMEOUT_SEC`），sidecar 侧读 worker 回复的上限是 60 秒（`sidecar/src/browser.cpp` 的 `BROWSER_RESPONSE_TIMEOUT_MS`，超时会杀掉 worker）。**预检 + 点击 + 等待三者加起来必须留在这个预算内** —— 预检若也按 30 秒去等元素，单次点击会到 60 秒并被杀。
- 测试侧每条命令的读数预算是 45 秒（`browser_worker_test.dart` 的 `send()` 超时），超过只会拿到 `worker response timeout`。

## Goals / Non-Goals

**Goals:**

1. 点击**确实会开新标签页**的元素时，新页晚于 1 秒才注册也要被跟随（AI 读到的必须是真正的落地页）。
2. 普通点击（原地跳转）**不多等**：等待窗口与现在一致。
3. "该开新页却没等到"这件事**可观测**，不静默。
4. 有一条**确定性**的复现用例：不依赖机器忙不忙，在改动前的代码上**稳定失败**，改完**稳定通过**。

**Non-Goals:**

- **不给"锚点没有 `target`、由页面的 JS 开新页、且晚于等待窗口"这一类加支持**。判据只有点击前的 `target`，而字符串匹配点击处理器太脆（拼接、包装、事件委托都会绕过它）。现状就是跟不上，本变更把它如实写进规范（界内才必须跟随），不做假承诺。**要改这一类的唯一办法是"每次点击都多等"，代价落在最高频的操作上，本变更明确不付这个代价。**
- 不动 `ctest` 里那条联网搜索用例的不稳定（另一件事，另行立项）。
- 不改"窗口隐藏 / 最小化 / 被遮挡"相关的任何行为。
- 不改多标签页管理方式：新页照旧被跟随、原页照旧保留、会话关闭仍是兜底。
- 不新增任何对模型可见的字段或计数。

## Decisions

### D1 点击前先判断"这个元素会不会开新标签页"

用一次 DOM 读取取到目标元素的 `target` 属性（`target="_blank"`，或等价的具名/新窗口目标）。判断结果是**布尔值**，只决定"这次点击用长窗口还是短窗口"。

**这次读取必须是有界的、不等待元素的**：用不等待的取值方式（例如在页面里执行 `document.querySelector(选择器)` 再读属性，元素不在就得到空），或给等待式取值一个显式的小超时（取 500 毫秒以内）。**为什么**：worker 从不设置 Playwright 的默认超时，未显式传超时的等待式取值会继承默认的 30 秒；预检 30 秒 + 点击 30 秒 = 60 秒，正好撞上 sidecar 的 60 秒上限（超时即杀 worker），而测试侧 45 秒就会先返回 `worker response timeout` —— 那样 tasks 里"选择器不存在时错误仍是选择器超时"这条判据会以与本次改动无关的理由变红。

**读取失败一律按"不会开新页"处理**（选择器不匹配、元素已被移除、执行出错、超时），走现在的 1 秒路径，**绝不因为判断本身失败而让点击失败**。

### D2 判定"会开新页"时，这一次点击用更长的有界窗口，且从点击返回之后起算

`target="_blank"` 的点击用 `NEW_TAB_WAIT_SEC = 5`（秒）；其余点击继续用 `NEW_PAGE_WAIT_SEC = 1`。两个窗口都是**上界**：新页一到就立即返回，不会白等。

**起算点必须改**：现在的写法把 `page.click(...)` 包在 `expect_page` 块里，计时从点击**之前**开始，点击自身的可操作性等待会吃掉弹窗预算（"机器忙"正是这一类的典型）。改法：先记下点击前的页面集合、执行点击、**点击返回之后**再有界地等新页事件（例如点击后 `wait_for_event("page", timeout=...)`；点击期间就已注册的新页由"点击前页面集合"这一层兜住）。这样"5 秒"才真的是"点击后 5 秒"。

**备选与否决理由**：

- **把全局窗口直接调到 5 秒** —— **否**。没有弹窗时 `expect_page` 会把整个窗口等满。全局调到 5 秒，等于**每一次普通点击都多等 4 秒**，代价落在最高频的操作上。
- **不再依赖等待窗口，改成"点完之后循环看页面集合"** —— **否**，理由见 D3（本项目已实测否决过）。

### D3 不做"超时后再看页面集合"这一层（本次审查后删掉的设计）

原先的设计里有一层兜底：超时之后再看一眼 `context.pages`，多出来的页就跟随。**删掉**，四条依据：

1. **时窗算术上必然看不到**：非 `target` 的点击用 1 秒窗口，补看发生在窗口到期（约 1 秒），而要让补看有意义的新页至少也得在 1 秒之后才注册（1.5 秒那类）—— 补看早于它。
2. **这个做法已被实测否决**：归档变更 `2026-09-13-add-browser-tool` 的任务记录里写着"轮询 `context.pages` 在新页打开后读不到（弹窗事件只在 Playwright 的 API 泵动时才冲洗出来）"。那是一次真实测量，不是推测。
3. **本机这个 Playwright 版本的实现也支持这个结论**：`context.pages` 是本地读（不经过事件泵），一次读看不到尚未冲洗的晚注册页。
4. **收益几乎为零**：`expect_page` 已经覆盖了窗口内**所有**开页事件；补看能多覆盖的只有"窗口到期之后、补看之前那几毫秒内注册"的极窄情形。

**代价如实记**：删掉这一层之后，"锚点没有 `target`、由 JS 开页、且晚于窗口"这一类仍然跟不上（Non-Goals 已写明）。真要覆盖它，只能把"每次点击都多等"付出去，或者做**会泵动事件的有界轮询** —— 后者是个独立方案，需要自己的实测判据（见 Open Question 2），不在本变更里偷偷塞进去。

### D4 "该开新页却没等到"要记一笔，落点写死

当 D1 判成"会开新页"、但长窗口内没有新页时，在 **per-call 记录**（stderr 的 `browser-record:` 行）里加一个布尔键 `expected_new_tab_unfulfilled: true`。

- **值怎么来**：挂在会话属性上、由 `_emit_record` 读取（与既有 `_read_permissions` 的做法一致 —— 它的注释写着"挂在会话上，这样记录里能带上、又不会泄漏进模型可见的快照文本"）。
- **不得**出现在 `_handle_click` 的返回字典里（那份字典会被原样打印到 stdout，是模型可见内容），**不得**变成失败。
- **为什么不用现成的 `_log()`**：它打出去的行前缀是 `WORKER:`，而测试侧只认 `browser-record:` 前缀 —— 用 `_log` 写，测试看不见，判据就写不出来。
- **顺带把防泄漏断言收紧**：既有测试用的是"五个键名不许出现在模型可见返回里"的黑名单，新增第六个键不会被它抓住；改成"模型可见返回的键集合等于允许集合"（白名单式）。
- **为什么不改成模型可见的报错**：这不是失败（可能用户自己拦了弹窗、或页面取消了默认行为），把它变成报错会污染模型看到的内容。

### D5 判据：确定性复现，不靠"机器忙不忙"

测试页**必须由本地 HTTP 服务提供**（复用既有用例的写法：`HttpServer.bind(InternetAddress.loopbackIPv4, 0)` 加一条 `/landing` 路由）。**为什么不能用 `data:` URL**：既有用例的注释写着 Chromium 不会把新标签页导航到 `data:` URL，而 `window.open('/landing')` 也需要一个真实的源。

页面里放一个链接 `id='slow'`：`target="_blank"` + 点击处理器先 `preventDefault()` + `setTimeout(() => window.open('/landing'), 1500)` —— 新标签页**必然晚于 1 秒窗口、早于 5 秒窗口**才开。

- **改动前**：1 秒窗口错过它 ⇒ 不跟随 ⇒ 快照还是原页面 ⇒ 用例**稳定失败**。
- **改动后**：这次点击被判成"会开新页" ⇒ 用 5 秒窗口 ⇒ 1.5 秒时事件到达 ⇒ 跟随 ⇒ 用例**稳定通过**。

**断言口径与既有那条用例一致（五条）**：返回 `ok` 为真、快照含 `LANDING`、点击记录 `browser_opened > 0`、`adopted_tabs > 0`、`tabs >= 2`。

**红必须可归因**：记录里的这几个计数是在 `_handle_click` 返回**之后**才求值的，那时 1.5 秒的弹窗还没发生 —— 只打印点击返回的 JSON 分不清"等到 1 秒就走"和"弹窗根本没开"。所以红态还要多一步：点击之后**再发一次 snapshot**（时点放在弹窗之后），断言它的记录里 `tabs >= 2`（新页确实开过）而点击记录 `adopted_tabs == 0`（没跟上）。**这样红才等于"晚到"，而不是"页面写坏了"。**

## Risks / Trade-offs

- **["锚点没有 `target`、由 JS 开页、晚于窗口"仍然跟不上]** → Non-Goals 已划界，规范已收窄成"界内注册才必须跟随"。要改得付"每次点击都多等"的代价，另行立项。
- **[`target="_blank"` 但实际不开页的点击会多等满 5 秒]**（例如处理器里 `preventDefault` 且不开窗）→ 只影响这一类；窗口是上界，开了就立即返回。这是本设计换来的确定性所付的代价。
- **[被判成"会开新页"、而点击自身失败的点击，返回错误的时间也会从约 1 秒变成约 5 秒]**（`expect_page` 的块在超时退出时要把窗口走完）→ 与上一条同一类代价，如实记；D2 把起算点改到点击之后会明显缓解（失败的点击返回后只需再等一小段）。
- **[D1 的预检读取可能失败]**（选择器失效、元素被移除、执行超时）→ 一律按"不会开新页"处理，走现在的 1 秒路径，**绝不因为预检失败而让点击失败**；预检的时限与预算见 D1 的约束。
- **[长窗口让某条用例总时长变长]** → 只有"判成会开新页却不开窗"那条用例真会付满 5 秒；单条命令 5 秒远低于测试侧 45 秒与 sidecar 60 秒的预算。
- **[改动会动到浏览器 worker 这个长期存活进程]** → 回滚就是还原这一个文件；不涉及数据、表结构、配置格式。那条新用例保留（它在旧代码上红，正好是守卫）。

1. 先加 D5 的确定性用例，在**没改 worker** 的代码上跑一遍，贴出**连跑 3 次都红**的输出（红态先落地，并且红得可归因）。
2. 再改 `_handle_click`（D1 → D2 → D4），顺手把 `_install_page_handler` 里那句与代码不符的注释改对。
3. 跑该用例 ⇒ 绿；跑整个 `browser_worker_test.dart` ⇒ 全绿；跑 `flutter analyze` 与语法检查。
4. 反例构造：把 `NEW_TAB_WAIT_SEC` 也改成 1.0 ⇒ 那条用例必须变红（证明红确实由"窗口太短"造成）；改回来 ⇒ 必须变绿。
5. 全量 `flutter test` 连跑 3 次（**会开浏览器窗口，由主循环自己一次一件地跑，不派子 agent**），作为附加观测（它的区分力弱：这条用例原来约一半概率红，三次全绿有约八分之一的概率是碰巧）。
6. live 层：跑 `integration_test/browser_live_test.dart`（真实模型驱动、正好覆盖"点搜索结果并读落地页"），读 `test/live_visual/` 下截图做视觉验收，并按 `Docs/TESTING.md` 的 OS 级窗口要求补一张全屏截图。

## Open Questions

1. **`NEW_TAB_WAIT_SEC = 5` 这个数够不够？** 它是上界、且只在判定会开新页时生效。**处置**：先用 5 秒；收口时用一条"窗口 + 1 秒才开窗"的变体用例给出下界证据（例如把延迟设成 3 秒，断言仍被跟随），而不是靠"没见到更晚的情形"这种没有数据来源的话。若将来要按真实分布调这个数，得先在记录里加一个"点击到新页注册耗时"的读数 —— 现在没有任何这样的读数（这条如实记下）。
2. **要不要给"没有 `target`、JS 开页"这一类做会泵动事件的有界轮询？** 本变更不做（Non-Goals）。**何时可以重新考虑**：等有办法不把代价摊到每一次普通点击上时（例如只在"点击后页面没有任何变化且当前域名与预检结果不符"这类条件下才多等），并且那一次必须自带实测判据。
