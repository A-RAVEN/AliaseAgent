## MODIFIED Requirements

### Requirement: Stay-hidden default and follow-new-tab (design 甲)
The system SHALL NOT call per-step bring-to-front. The system SHALL implement the mechanisms for `alert`/`confirm` auto-handling, download/permission suppression via a download cancel and Playwright's default auto-denial of permission requests / auto-dismissal of dialogs (no permission is granted; the worker additionally grants NO permissions up front via `grant_permissions([])`), and — per design 甲 (the user-chosen design decision) — SHALL FOLLOW a newly-opened page (a click on a `target=_blank` result / a `window.open` popup) rather than closing it, so the AI reads the real landing page the click produced — WITHIN THE BOUNDED WAIT THAT BELONGS TO THAT CLICK: the worker SHALL decide that bound before clicking by reading the clicked element's target (`target=_blank` and equivalent named/new-window targets get the longer bound, every other click keeps the ordinary bound), both bounds being upper bounds only (the worker proceeds as soon as a new page appears); an ordinary in-place click SHALL NOT wait longer than it does today; a page that registers only after that bound is NOT followed — the click then returns its in-place result, and when the pre-click check expected a new page the worker SHALL record on its observability channel that a new tab was expected but not observed (never in the model-visible response, never as a failure); a failure to perform the pre-click check SHALL be treated as "does not open a new page" and SHALL NOT fail the click; the original tab stays open and the AI manages multi-tab via the session (session-close is the fallback). The original "single-tab reuse via an explicit popup/new-tab close handler" is REMOVED by design 甲. Whether, on a triggering page, those mechanisms hold (no dialog, no download/permission granted) is external browser behavior: change task 1.4 confirmed alert/confirm auto-handling (dialog_count=2, page alive), download denial (dl.cancel() or accept_downloads=False, no file persisted), and that window.open + target=_blank open a new page (which design 甲 now FOLLOWS rather than closes). Permission suppression was confirmed by change task 1.6 on a real HTTPS secure-context page (permission.site): Playwright automation auto-denies permission requests by default — Notifications permission.query becomes 'denied' and Notification.requestPermission() resolves 'denied'; geolocation was not granted (getCurrentPosition returned error 3, a TIMEOUT — the request could not obtain a position within the 6s test timeout; permission.query stayed 'prompt', not 'denied'). Therefore no permission is granted (notifications denied; geolocation not granted). Design 甲 additionally calls `grant_permissions([])` at context creation (spike 2026-09-08: removes Bing's `edge://permission-request-dialog/`), which — as measured on the local worker record — makes BOTH notifications and geolocation report 'denied' (a stricter no-grant than task 1.6's geolocation 'prompt', since grant_permissions([]) explicitly denies up front). No permission prompt is surfaced is confirmed for the Notifications path (Playwright auto-denies); for geolocation the permission.state stayed 'prompt' (undecided/pending) in the task-1.6 measurement, so the no-prompt behavior is NOT demonstrated for geolocation there (though design 甲's grant_permissions([]) now denies it up front in the worker). Honest caveat: the geolocation case timed out (error 3) rather than being permission-denied and left the permission undecided, so it was not granted but the no-prompt behavior is not established for it. The tool SHALL NOT raise the window on its own per-step actions; any deliberate raise requires a separately-defined visibility-request mechanism, which is out of this change's scope (a future change).

#### Scenario: Minimized window stays minimized during automation
- **WHEN** the tool runs navigates/clicks while the window is minimized
- **THEN** if task 1.2 confirmed the window can be held minimized, it stays minimized and the tool does not raise it; otherwise the tool applies `--disable-backgrounding-occluded-windows` and operates user-visibly rather than claiming hidden-by-default; the outcome is recorded by task 1.2, not asserted as guaranteed. The occluded-by-an-overlapping-window case was measured by task 1.5 (a fullscreen topmost opaque window over the browser: commands execute, snapshot fresh, no render throttle), so the tool's off-screen execution holds for occlusion too.

#### Scenario: Clicking a result follows the page it opens
- **WHEN** the agent clicks a result link that opens a new tab (`target=_blank`) or a `window.open` popup
- **THEN** the tool SHALL FOLLOW that newly-opened page (make it the active page, wait for it to load, snapshot it) so the AI reads the real target page, provided the page registers within the bound that belongs to that click (the longer bound when the pre-click check judged the click opens a new page); the original tab stays open; the tool records the browser-opened / adopted-tab counts as observable. This is design 甲 — the original single-tab close (which dropped the landing page) is removed.

#### Scenario: Dialogs are handled, downloads denied, permissions not granted
- **WHEN** a page triggers an alert/confirm, or a download/permission prompt appears
- **THEN** the tool denies downloads by cancelling them, and relies on Playwright's default auto-dismissal of alerts/confirms and auto-denial of permission prompts (plus `grant_permissions([])` so no permission is granted up front); whether no dialog / no download / no permission-grant holds is confirmed by task 1.4 (alert/confirm auto-handling, download denial) and task 1.6 (no permission granted). The permission case was confirmed by task 1.6 on an HTTPS secure-context page: no permission granted (notifications denied; geolocation not granted — it timed out, permission.state 'prompt'). The tool SHALL NOT grant permission; Playwright's default auto-denial denies permission prompts (confirmed for the notifications path; for geolocation the permission.state stayed 'prompt'/undecided in the task-1.6 measurement, so the no-prompt behavior is not established there — though design 甲's `grant_permissions([])` denies geolocation up front in the worker record).


#### Scenario: A new tab that registers later than the ordinary wait is still followed
- **WHEN** the agent clicks a `target="_blank"` link whose new page registers after the ordinary wait window has already expired (measured case: the page opens about 1.5s after the click, the ordinary window is 1s, and the bound for such a click is 5s)
- **THEN** the tool SHALL follow that page (make it the active page, wait for it to load, snapshot it), so the response carries the landing page rather than the page that was clicked

#### Scenario: An ordinary in-place click pays no extra wait
- **WHEN** the agent clicks an element that does not open a new page
- **THEN** the tool SHALL keep today's wait window (no additional delay), and the click's response SHALL be produced as it is today

#### Scenario: A judged new-tab click that opens nothing is recorded, not failed
- **WHEN** the pre-click check concluded the click opens a new page, but the new page does not register within the bound for that click
- **THEN** the tool SHALL still return a successful response for the click (the in-place outcome), and SHALL record on its observability channel that a new tab was expected but not observed

#### Scenario: The pre-click check itself failing never fails the click
- **WHEN** the pre-click check (reading the clicked element's target) cannot be performed, e.g. the selector no longer matches or the element is removed
- **THEN** the tool SHALL proceed with the ordinary wait window as if the element does not open a new page, and SHALL NOT report the click as failed because of the pre-check
