## Context

用户 2026-10-05 在探索里定死了这个环的形状（原话）：

> 「不是各自从12点开始，而是从上一层结尾开始，和上下文的顺序一样，从12点开始的是2级摘要，然后一级摘要，然后原文，3者的长度总和恰好是上下文占用进度」

现在仓库里的相关事实（都是读代码读到的，不是猜的）：

- 压缩拼投影时，一趟请求的内容由一条**时间线**决定：`lib/main.dart` 里 `_resolveSummaries` 返回 `List<ProjectionPiece>`，每一段要么**发摘要**（`summary` 非空，段自己带 `level` = 1 或 2），要么**按原文发**（`summary` 为空）。时间线按内容在历史里的位置排好，所以顺序天然是「二级摘要 → 一级摘要 → 原文」。
- 关键的坑：**一个段是不是一级摘要，和这一趟是不是按摘要发它，是两件事**。已经被压成一级摘要、但位置还不够远的那一段，这一趟仍然按**原文**发（`_resolveSummaries` 里 `sentAsSummary` 的判据）。所以三段必须按「这一趟实际发出去的表示」分类，不能按 `level` 分类。
- 三段各自的数字都有现成的来源：发摘要的那段用 `SummaryResult.tokens`（模型返回的**实测** `output_tokens`）；按原文发的那段用 `CompactionEngine.rawTokens(...)`（仓库既有的估算器 `ContextEstimator`，`_charsPerToken = 4`）。这两个数就是 `projectedTotal` 已经在用的那两个。
- 界面顶部那一行现在只有「对话视图 / 真实上下文」两个按钮，右侧是空的（`ChatScreenState.build` 里的 `Align` + `SegmentedButton`）。
- 系统提示词与工具定义**不在**压缩的账里：`projectedTotal` 只累加消息。它们每次请求都要发，且永远不会被压缩。
- 主题只有一套：`ColorScheme.fromSeed(seedColor: Colors.deepPurple, brightness: Brightness.dark)`。
- 实测（本机 `~/.aliasagent/aliasagent.db`，只读查询）：历史最大的一次请求 `input_tokens = 7340`，而同一请求里对话正文只占几百 token，剩下约 6 千是系统提示词加 14 个工具定义；`summary_nodes` 表为空，也就是这个库里从来没产出过摘要。

## Goals / Non-Goals

**Goals:**

- 在界面上如实显示「这一轮请求里，二级摘要 / 一级摘要 / 原文各占多少、加起来占了模型窗口多少」。
- 三段的口径能被一条命令核到：面板上每个数字都要写明它是实测还是估算。
- 记录下来的这份拆分，必须和「真实上下文」那一屏描述的是**同一份请求**。

**Non-Goals:**

- 不改压缩的任何机制：阈值、触发时机、分层规则、分批、合成判据一个字都不动（那套是用户钉死的，见 `TODO.md` 顶部的四条硬约束）。
- 不加手动触发压缩的按钮。
- 不画 25% / 75% 那两条阈值刻度线（用户没要求；阈值是配置项，画上去就得跟着配置变，属于另一个变更）。
- 不改「真实上下文」那一屏的渲染，也不合并这两个东西。
- 不做历史趋势图、不做占用曲线。

## Decisions

### D1 三段怎么分类：按「这一趟实际发出去的表示」，不按层级

对时间线逐段判断：`summary == null` ⇒ 这一段这一趟走的是原文，计入**原文**；`summary != null && segment.level >= 2` ⇒ 计入**二级摘要**；`summary != null && segment.level == 1` ⇒ 计入**一级摘要**。

依据：`_resolveSummaries` 已经用同一条判据决定每一段发什么，环必须和它一致，否则会出现「界面上说这段已经是一级摘要，而实际发出去的是原文」这种假话。

被否决的做法：按 `segment.level` 分类。理由：会让「已压成摘要但还不够远」的段被算进摘要色，而它实际是按原文发的。

「够不够远」的判据本身（`CompactionEngine.substitutesSpan`，距离 = 比它更新的所有原文的估算 token 之和，一级要超过阈值 T、二级要超过 2T）不改，环只是读它的结果。

### D2 数据模型：一个纯值对象，和一个可单测的纯函数

新增 `lib/models/context_breakdown.dart`：

```
class ContextBreakdown {
  final int level2Tokens;        // 二级摘要（实测 output_tokens 之和）
  final int level1Tokens;        // 一级摘要（实测 output_tokens 之和）
  final int rawTokens;           // 原文（估算）
  final int fixedOverheadTokens; // 系统提示词 + 工具定义（估算）
  final int windowTokens;        // 模型窗口；<= 0 视为未知
  int get usedTokens => ...;     // 四项相加
  static ContextBreakdown fromTimeline({required List<ProjectionPiece> timeline, ...});
  static ContextBreakdown verbatim(...);  // 没有走压缩那两条路径时的退化形式
}
```

同一个文件里把 `ProjectionPiece` 从 `lib/main.dart` 搬过来（它现在定义在 `lib/main.dart` 顶部，是个纯数据类）。

理由：分类逻辑是这个变更唯一容易写错的地方，把它做成纯函数就能用 `test/unit` 直接喂各种时间线来验；留在 `lib/main.dart` 里则只能靠启动整个应用来测。搬迁只改定义位置，名字与用法不变。

`verbatim` 那条路径不另写一套分类：等价于「整条时间线只有一个按原文发的段」，实现上复用 `fromTimeline`。

### D3 记录时机与载体：并进已有的上下文快照

`ContextSnapshot`（`lib/services/context_snapshot.dart`）增加一个字段承载 `ContextBreakdown`，在 `lib/main.dart` 里 `apiMessages` 定下来之后、与现有那次 `setState` **同一次**写进去。

理由：环和面板与「真实上下文」那一屏必须描述同一份请求。分两次 setState 会存在一帧「快照换了、拆分还是上一次的」的不一致状态，面板这时点开就是错的。并进同一个对象从结构上消灭这种可能。

字段带缺省值（`null`），既有构造点与既有测试不受影响；为 `null` 时环不渲染。

### D4 环的几何：整圈 = 窗口，三段首尾相接，从 12 点起

- 整圈 = `max_context_tokens`。
- 每一段扫过的角度 = 该段 token 数 ÷ 窗口 × 360°。
- 起点 -90°（12 点方向），顺时针依次画 二级 → 一级 → 原文。
- 三段加起来是这一轮**对话消息**那部分的占用（**不含**系统提示词与工具定义，见 D5）；剩下的圈是剩余窗口。
- 三段长度都是 0 也照常画轨道（空环）。
- 记录时机：必须与 `ContextSnapshot` 同一次 `setState`，而且是**每次发送前那一处** —— 工具轮里每次发送都会重建快照（`lib/main.dart` 里那段注释写着「The last send of a multi-round turn wins (the grown version)」），所以拆分若只在循环外算一次，最后一轮的快照与拆分描述的就不是同一份请求。工具轮追加进请求的消息按原文计入。

尺寸：**直径 20 逻辑像素、描边 2、半径由前两者算出（(20 − 2) ÷ 2 = 9）、起点 12 点**。**来源：用户 2026-10-18 明说「可以 20」** —— 这是用户要求的数字，不是从 dsh 参照物量出来的。原值 14 才来自 dsh（用户原话「类似 dsh 这样的一个圆环」）；本机实测用户自己 dsh 窗口里那个环是 **19 物理像素 ≈ 15.2 逻辑像素**（`HKCU\Control Panel\Desktop\WindowMetrics` 的 `AppliedDPI = 120` ⇒ 125% 缩放），只比 14 大 1～2 像素，所以照 dsh 放大根本不会显眼 —— 这也是用户改成 20 的原因。
（`dsh-client-ui-conversation/lib/client.js` 这份参照文本机**不存在**，`Test-Path` 为假、全仓也没有 `client.js` / `ContextMeter`；所以 14/2/5.5 只能按「产品里已有的常量」对待，本地拿不出原始参照物复核。）

被否决的做法：三个同心圈各画一圈。理由：用户明确说了是「从上一层结尾开始」，三段是接力的，不是各自独立计量的。

### D5 固定开销（系统提示词 + 工具定义）不占环上的颜色

环上只有三段，加起来是**对话消息**那部分；系统提示词与工具定义单独在面板里列一行，并写明环不含它们。

理由三条：① 用户在上下文顺序里排的是三段，系统提示词在请求里比二级摘要还靠前，插进去就变成四段，与用户的定义冲突；② 它是常数、不随对话增长，而环的用途是看对话在长；③ 实测它约占窗口的 0.6%，画在 14 像素的环上是一根看不见的线，占颜色反而让人以为「这里有一大块」。

它的数字用仓库既有估算器算：`ContextEstimator.estimateTokens(systemPrompt) + ContextEstimator.estimateTokens(toolsJson)`，面板里标成估算。**来源**：`lib/services/context_estimator.dart` 是仓库既有的估算器，压缩的账本来就用它。

### D6 点击环弹出只读面板

用 `showDialog` 弹一个只读面板（标题 + 若干行 + 一个「关闭」按钮），点遮罩关闭。

理由：仓库里既有的弹窗做法就是 `lib/ui/setup_dialog.dart` 这一种；`showDialog` 自带点外面关闭，不用自己写「点面板外面就关」的逻辑与它的测试。

面板内容与顺序（每一行都标来源）：

| 行 | 数字 | 来源标注 |
|---|---|---|
| 二级摘要 | `level2Tokens` | 实测 |
| 一级摘要 | `level1Tokens` | 实测 |
| 原文 | `rawTokens` | 估算 |
| 系统提示词 + 工具定义 | `fixedOverheadTokens` | 估算；并写明「环上不含这一行」 |
| 合计 | `usedTokens` | 上面各项相加 |
| 占模型窗口 | **一个**百分比：`conversationTokens / windowTokens`（与环旁那个数字同口径，见 D10；用户 2026-10-16 裁定只给一个数） | —— |

面板底部复用 `CompactionStatusBanner.contextViewNote` 那句「下面是上一次实际发出的内容，压缩结果下次发送时才出现」，与「真实上下文」那一屏的说法保持同一句话。

### D7 什么时候不画环

- `max_context_tokens` 缺失或 ≤ 0：不画。依据：`lib/main.dart` 里 `if (maxContextTokens > 0)` 决定压缩整套是否启用；窗口未知时「占窗口多少」没有意义。
- 还没有任何快照（本次启动还没发过请求）：不画。依据：与「真实上下文」那一屏在没有快照时显示「尚无捕获的上下文快照」一致。

两条都渲染 `SizedBox.shrink()`，与 `CompactionStatusBanner` 空闲时的做法一致（不占高度、不加分隔线）。

### D8 数字格式

面板里的 token 数写原始整数（例如 `7340`），不做 K / 万 的缩写。理由：缩写会再引入一层四舍五入，而这个面板的用途就是核对数字。

### D9 颜色

三段与轨道各一个具名常量，取值来自主题 `ColorScheme`（不写死十六进制）：

| 用途 | 取值 |
|---|---|
| 二级摘要 | `colorScheme.primary` |
| 一级摘要 | `colorScheme.tertiary` |
| 原文 | `colorScheme.outline` |
| 轨道 | `colorScheme.surfaceContainerHighest` |

**这三个颜色是我选的**：用户只说了「3 种颜色」，没有指定是哪三种。集中成常量表，将来要换只改一处。

### D10 环旁给一个百分比数字，口径 = 环上三段（2026-10-16 追加）

真机跑通之后发现环几乎看不见（Risks 里那张表给了算术：4.5% 折合 1.6 像素弧长）。结论是**数字才是那一档占用下唯一读得出来的东西**，所以：

- 数字的位置：**在环的左边**，而且它必须是 `ContextRing` 的**兄弟节点**（在 `lib/main.dart` 那一行 `Row` 里、`ContextRing` 之前），**不许画进 `ContextRing` 内部** —— 后者会把 `find.byType(ContextRing)` 的尺寸从 14×14 顶掉，而已勾的 5 处断言正是按 14×14 比的（见 tasks 9.2）。
- 位置依据：右边只剩 **12** 像素（= `lib/main.dart` 里那一行的 `EdgeInsets.symmetric(horizontal: 12)`；实测 1266 − 1253.6 = 12.4），放不下那个百分比文本。**文本宽度已实测 = 57.5 像素**（`test/widget/context_ring_test.dart` 那条用例在断言之上打印 `文本宽度=57.5`；57.5 远大于剩下可用的 12 像素，所以只能放左边 —— 原来这里写的"量级估算 30～40 像素"已被实测替换）。
- 字号与颜色 SHALL 复用主题里既有的文本样式与语义色，**不 invent 新尺寸**（AGENTS 第 9 节：尺寸与上下限都要能溯源）。
- 分子 SHALL 是 `conversationTokens`（二级 + 一级 + 原文），**SHALL NOT** 是 `usedTokens`（四项）—— 固定开销不在环上，用四项算出来的数字与弧长对不上。
- 格式与面板一致：两位小数 + `%`（沿用面板已有的 `toStringAsFixed(2)`，不新造一套）。
- 三段改成**实心扇形**（附带改动）：零代价，但按上面的算术只提升 1.35 倍，**它不是这个问题的解**，不要把它当成解。

被否决的做法：

- **只把环画大**（例如 14 → 20 像素）：14 这个数来自用户点名的 dsh 参照物，改它要用户定；而且面积按半径平方长，放大 2 倍也只有 4 倍面积，仍不如一个数字可靠。
- **整圈改成压缩阈值 T**：效果最好（4.5% → 18%），但它改的是「这个环在量什么」，而「整圈 = 窗口」是用户钉的口径；本 change 的 Non-Goals 也把阈值刻度划给了另一个变更。**用户 2026-10-16 裁定：维持窗口口径**，所以本 change 只做"环 + 数字"，不做阈值刻度。
- **把「占模型窗口」那行写成两个百分比**（环上三段 / 合计各一个）：**用户 2026-10-16 裁定只给一个数**，且这个数必须与环旁那个同口径（环上三段），系统提示词与工具定义只作为单独一行的数字出现、不进百分比。


## Risks / Trade-offs

- **[占用很低时环几乎看不见]** → 实测本机历史最大的一次请求是 7,340 / 1,000,000 = 0.73%，画出来不到 3 度。这是如实显示，不做视觉补偿（补偿会让长度与数字对不上，比看不见更糟）；面板里的数字不受影响。要不要更醒目属于另一个变更。
  **2026-10-16 复核（真机跑通之后）**：这条风险是实的，而且比写的更严重。真机那一次 `raw=45021 / 窗口 1000000 = 4.5%`，在半径 5.5 像素上折合 **1.6 像素弧长** —— 截图里根本看不见（把那一角放大 6 倍才认出来）。
  三个候选改法连同**算出来的**效果（不是估计）：
  | 改法 | 4.5% 时的可见面积 | 判断 |
  |---|---|---|
  | A 把细描边弧改成实心扇形 | 3.2 → 4.3 平方像素（**只多 1.35 倍**） | 零代价，但**不足以解决**问题，只作为附带改动 |
  | B 环旁给出百分比数字 | 文字不随比例缩小 | **采纳** —— 这是唯一在小占用下仍然可读的东西 |
  | C 整圈改成压缩阈值 T 而不是整个窗口 | 4.5% → 18%，弧长 6.2 像素 | **不采纳（留给用户决定）**：它改的是"这个环在量什么"，而"整圈 = 窗口"是用户钉的口径；本 change 的 Non-Goals 也把阈值刻度划给了另一个变更 |
  因此新加 D10（见下），并且把面板「占模型窗口」那一行的口径写清 —— 环上画的是**三项**之和，面板那一行原本用的是**四项**合计，两者对不上。

- **[环显示的是上一次发出去的，压缩期间不变]** → 面板底部写明这件事，复用「真实上下文」那一屏已经有的那句话。
- **[三段混用了实测与估算]** → 面板逐行标来源，不笼统写「约」。摘要的数是接口回的 `output_tokens`，原文的数是 4 字符≈1 token 的估算，两者精度不同，标出来比藏起来好。
- **[面板的合计与接口回的 `input_tokens` 不会完全相等]** → 合计是各部分的估算相加，接口的 `input_tokens` 还含消息与工具的 JSON 结构开销。面板只承诺「各部分的构成」，不承诺等于 `input_tokens`；这一点写进面板的说明文字。
- **[环与「真实上下文」那一屏的口径不同（环不含系统提示词与工具）]** → 面板里写明环画的是哪一部分；两处不互相引用数字。

## Migration Plan

无数据迁移、无配置变更、无接口变更。回退方式：删掉 `lib/ui/context_ring.dart` 与顶部工具栏那一处接线、`ContextSnapshot` 的新字段留空即可，压缩机制完全不受影响（本变更不修改任何既有行为）。
