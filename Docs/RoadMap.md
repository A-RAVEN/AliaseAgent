# RoadMap

> 这份文件只讲**顺序与理由**：先做什么、为什么是这个顺序、哪一步是哪一步的前提。
> **可以勾选的待办条目只有一份，在根目录 `TODO.md`** —— 这里不复制清单，避免两处真相打架。
> 每个阶段做完，回来改本节的状态行，并在 `TODO.md` 里勾掉对应条目。

## 一、判断依据（为什么是这个顺序）

1. **先修"看得见内容不全会丢"的问题**。工具输出只留尾部会丢掉构建的第一条错误 —— 这是每天都会踩的痛，而且修法明确、不牵动架构。
2. **再修"状态是全局的"问题**。今天 sidecar 的工作区根、结果缓冲、浏览器 worker 都是进程级单例，因此**任何并发都不可能安全**。不先把它们变成"每 agent 一份上下文"，后面谈并行、谈子 agent、谈多 agent 都是空话。
3. **并发本身要分层**：先让只读工具并行（便宜、风险低），再谈子 agent。
4. **子 agent 优先于多 agent 团队**。子 agent 用一个新上下文解决"上下文装不下"，复用现有的一切；多 agent 团队要共享状态、冲突仲裁、成本配额，收益在单人桌面工具里并不明显。
5. **进程隔离是"等崩怕了再做"**。它真正的收益是崩溃隔离（今天 C++ 一崩整个 App 跟着死），代价是流式回调要改成跨进程帧协议。前提是第 2 步的句柄化 API 先落地。

## 二、阶段

### 阶段 1 —— 工具输出的交付契约（进行中）

- **change**：`openspec/changes/spill-large-tool-output`
- **状态**：proposal + 3 份 delta 已完成、`openspec validate` 通过；design 与 tasks 待写
- **做完的标志**：一条构建命令失败时，头部的第一条 error 在结果里可见；任何超限输出都能用 `read_spill` 按偏移读回，且逐字节一致
- **为什么第一个**：修法明确、不牵动架构，且它先把"输出怎么交付"这套契约定下来，后面子 agent 回传结果时可以直接复用

### 阶段 2 —— 上下文句柄化（未立项）

- **做什么**：`sidecar` 增加 `create_context` / `dispose_context`；`g_workspace`、十几个 `g_*_result`、浏览器 worker 全部变成"每上下文一份"；其余导出函数首参改成句柄
- **做完的标志**：两个上下文能同时存在且互不干扰（一个设工作区、另一个调工具，结果不串）
- **为什么第二个**：它是并发、子 agent、进程隔离三件事共同的前置。跳过它，后面每一步都要先绕开全局状态
- **依据**：`sidecar/src/tools.cpp` 的 `static std::string g_workspace`；`sidecar/src/sidecar_api.cpp` 的 `static std::string g_*_result`（注释自认 `thread-unsafe but single-threaded usage`）；`sidecar/src/browser.cpp` 的唯一 worker

### 阶段 3 —— 只读工具并行（未立项，依赖阶段 2）

- **做什么**：工具循环由"逐个 await"改成"按只读/写分组"；只读（read/grep/glob/web）并行，写类串行
- **做完的标志**：一个回合里同时发 3 个 `read_file`，总耗时明显小于串行；同时发 `write_file` + `read_file` 时顺序仍被保证
- **为什么第三个**：它只在阶段 2 之后才有意义，而且它本身不引入新概念，是纯粹的效率改动

### 阶段 4 —— 子 agent 当工具（未立项）

- **做什么**：`spawn_subagent` 工具：开新上下文、只回传结论；独立取消、独立计量
- **做完的标志**：让子 agent 去翻 200 个文件，父对话的上下文占用只增加它的结论那几百 token
- **为什么第四个**：它是"上下文装不下"的正面解法；需要阶段 2（独立上下文）与阶段 3（不会互相拖慢）

### 阶段 5 —— 进程即 agent（未立项，长期）

- **做什么**：把上下文塞进独立进程，句柄改成"进程 + 会话 id"，用仓库里 `browser.cpp` 已有的 stdin/stdout JSON 帧协议
- **做完的标志**：故意让 sidecar 段错误，App 只报"这个 agent 挂了"，界面与其它会话不受影响
- **为什么不急**：它的主要收益是崩溃隔离；流式回调改成跨进程协议是整块工作量

### 阶段 6 —— 符号索引（未立项，看需要）

- **做什么**：给"找代码"提供定义/调用/所在文件的结构化查询，替代纯文本 grep 试错
- **为什么最后**：只在大仓库里才痛；而且有了阶段 4 的子 agent 之后，"翻代码"的 token 压力已经小很多

## 三、明确不做

| 不做 | 原因 |
|---|---|
| 文件快照 + 一键回退 | 用户否决：只是 git 的补充、用得少、静默回退会让模型上下文变成假的（台账第 24 条） |
| 命令审批 / 沙箱 / 危险命令拦截 | 用户否决：明确要零审批的全权限运行（台账第 25 条，`CLAUDE.md` 已写成立场） |
| 向量检索 / RAG | 这个项目里"找代码"靠名字与结构就够，语义相似度是次要的；符号索引更划算 |

## 四、维护规则

- 阶段推进时，先改 `TODO.md` 里对应条目的勾选，再回来更新本节的"状态"行；
- 新阶段插入时说明它**插在谁之前、为什么**；
- 本文件不写具体任务（那些在 change 的 `tasks.md` 里）。
