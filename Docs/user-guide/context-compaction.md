# 上下文压缩

## 这是什么

对话变长以后，模型装不下全部内容。应用会把**较早的那部分对话**交给模型压成一条摘要，之后的每轮请求里就用这条摘要代替原文，这样对话可以一直继续下去。

摘要是**自动**发生的，界面上没有开关按钮；要调就改配置。

## 什么时候会压缩

阈值这样算：

```
阈值 = 模型能装下的总 token 数 × compaction_threshold_percent ÷ 100
```

举个例子：模型能装 100 万 token，百分比是 25，阈值就是 25 万 token。

**攒够阈值就压，不等把窗口装满**：从最早的内容开始往后累加，累加超过阈值，就把这一批压成一条摘要。

**你不动的时候也会压**：一轮结束、空闲大约 2 秒之后，应用会自己把攒够的那批压掉（后台压缩）。这时界面上会出现同样的提示；你要是这时发消息，这次后台压缩会让路，不会拖慢你这一轮。

## 什么时候这一轮需要等压缩

**不是每次压缩都要等**。发消息时应用先算一件事：**这一轮要发给模型的内容占模型总上下文多少**（要发的原文 + 一级摘要 + 二级摘要，摘要按它生成时的实测 token 数算）。只有超过 `compaction_wait_threshold_percent`（缺省 75%）时，这一轮才等压缩做完再发；不到 75% 就直接发出去 —— 这时一个压缩请求都不发，攒过阈值但还没压的内容**按原文发**，压缩留给空闲时那次后台压缩。

| 这一轮要发的内容占比 | 会发生什么 |
|---|---|
| 不到 75% | 立刻发；不生成摘要；该压的内容等空闲时后台压 |
| 超过 75% | 先压完再发；界面上出现"正在压缩"提示（见下一节） |

阈值同样只按比例算：`等待阈值 = 模型能装下的总 token 数 × compaction_wait_threshold_percent ÷ 100`。缺省 75；写了非法值按 75 走，并在日志里打印一行。

**代价（如实说明）**：不等的那一轮不压，所以压缩被推给"空闲约 2 秒后自动压"那次。你要是连续快速发消息、一直不空闲，投影会一路涨到超过 75% 才压 —— 那一次的等待会比每次小批压更长（一次压一大批）。想让它更早等，把这个百分比调小即可（例如 40）。

两个数这样来：

| 数 | 从哪来 |
|---|---|
| 模型能装下的总 token 数 | 配置里 `agent_types` → `general` → `max_context_tokens`；不写就再弹一次欢迎对话框问你要 |
| 压缩阈值百分比 | 配置里 `compaction_threshold_percent`，缺省 25（也就是 25%）；写了 `0`、负数、大于 `100`、小数、字符串都会被当成没写，按 25 走，并在日志里打印一行提示 |
| 等待阈值百分比 | 配置里 `compaction_wait_threshold_percent`，缺省 75；非法值同样按 75 走并打一行日志 |

## 有两级

| 级别 | 做什么 | 什么条件下发生 |
|---|---|---|
| 第一级 | 把**一段对话**（若干条消息）压成**一条摘要** | 这一段累积超过阈值 |
| 第二级 | 把**已经生成的若干条第一级摘要**再合成**一条更粗的摘要** | 这些摘要合起来又超过同一个阈值 |

两级用的是**同一个阈值算法**，没有别的门槛。

## 界面上怎么认出来

**压缩进行中**，界面上直接能看到一条提示（不是压完才看得到）：

- 在「对话视图」里，它出现在输入框上方；
- 在「真实上下文」那一屏，它固定在最顶部，并写明下面显示的仍是上一次实际发出的内容。

提示会说明正在做哪一步（挑选分段主题 / 生成第几段一级摘要 / 合成二级摘要）与进度。空闲时自动跑的那次会多一句"发消息会让它先让路"。

界面文案：`你发消息会让压缩先让路`

压缩做完提示就消失。压缩后，摘要会当成**一条消息**发给模型，开头带一个标记：

- 第一级：`## 更早上下文(压缩xN,非用户发言)`
- 第二级：`## 更早上下文(压缩xN,层级2,非用户发言)`

想看到它：发几轮消息让对话变长，切到「真实上下文」那一屏（见 [真实上下文视图](real-context-view.md)），排在最前面的那条就是摘要。

## 原文去哪了

**还在本地数据库里**，没有删。只是这一轮的请求里不再发送原文，改用摘要。

## 会花钱

生成摘要要走一次模型调用 —— **这一步是要计费的**。阈值调得越低，压得越勤，调用越多。生成摘要时会带上一段更早的摘要当参考（这样相邻的摘要之间不会各说各话），因此每次摘要调用的输入会比过去多一点。

## 怎么调

改配置里的 `compaction_threshold_percent`（1 到 100 的整数），重启应用：

```json
{
  "agent_types": {
    "general": {
      "max_context_tokens": 200000,
      "compaction_threshold_percent": 25
    }
  }
}
```

- **调小**（例如 10）：更早开始压缩，单次请求更省 token，但更早丢掉细节。
- **调大**（例如 80）：保留更多原文，但单次请求更贵，也可能更快撞到模型上限。

## 压缩不会少给你内容

压缩**永远不会让内容变大**：每一级都比一下「压缩前」和「压缩后」的 token 数，**取小的那一边**当作这一级的内容。

- 摘要确实更短 ⇒ 用摘要，跟以前一样。
- **压不短**（模型给的摘要反而更长）⇒ 这一级就按**原文**发出去，一个块都不少（工具调用、思考块都保留），而不是把这段内容丢掉。

所以「压不短」不会让你少看到东西。

唯一一种例外是**装不下**的时候：这一轮要发的内容超过 `max_context_tokens`，应用会从**最旧的二级摘要**开始，把它们从这一轮的请求里拿掉，拿到装得下为止。这只是「这一轮不发」——**原文和摘要都还在本地数据库里**，一条都没删。一级摘要与原文永远不会因为装不下而被拿掉。

## 环怎么看

输入框右边、发送按钮左边有一个小圆环，旁边跟着一个百分比数字（对话视图与「真实上下文」两屏下都在原地）。

- **整圈 = 模型的上下文窗口**，也就是配置里的 `max_context_tokens`。
- **三种颜色，从 12 点顺时针依次是：二级摘要 → 一级摘要 → 原文**。每段扫过的角度 = 那一段的 token 数 ÷ 窗口。
- 剩下没上色的部分是这一轮还没用掉的窗口。
- **环上不含系统提示词与工具定义** —— 那两项每一轮都要发、且永远不会被压缩，单独在面板里列一行。
- 三段都是 0（比如刚清空对话）时，环仍然画出来，只是一圈灰轨道。

**没有摘要的时候为什么是一根单色弧**：那说明这一轮三段里只有「原文」不是 0（还没压出摘要，或者摘要段位置还不够远、这一轮仍按原文发），另外两段扫过 0 度，所以看上去只有一种颜色。

点一下环，弹出一个只读面板，逐行给数字，并注明每个数字是**实测**还是**估算**：

`界面文案：`上下文占用``

| 行 | 来源 |
|---|---|
| `界面文案：`二级摘要`` | `界面文案：`实测``（模型回来报的实际用量） |
| `界面文案：`一级摘要`` | `界面文案：`实测`` |
| `界面文案：`原文`` | `界面文案：`估算``（4 个字符≈1 token 的估算器） |
| `界面文案：`系统提示词 + 工具定义`` | `界面文案：`估算（环上不含这一行）`` |
| `界面文案：`合计`` | 上面各项相加 |
| `界面文案：`占模型窗口`` | 百分比（一个数，口径 = 环上三段之和，与环旁那个数字相同） |

底部那句话与「真实上下文」那一屏是同一句：

`界面文案：`下面是上一次实际发出的内容，压缩结果下次发送时才出现``

面板右下角是 `界面文案：`关闭``。

**环显示的是上一次实际发出去的内容**：压缩发生在发送之前，所以刚压完的那一轮，环和面板里还是上一次的数字 —— 下一次发送时才更新。合计是各部分的估算相加，不会刚好等于接口报回的输入用量（那边还含请求本身的 JSON 结构开销）。

## 限制

- **压缩是有损的**：原文不再发给模型，摘要里没写到的细节，模型就看不到了。
- **摘要是模型写的**：它可能漏掉或写错内容。想让某些内容永远不丢，把它们写进 `standing_requirements`（见 [配置](configuration.md)）。
- **没有手动触发按钮**：只能靠改阈值和对话长度来让它发生。
- **`max_context_tokens` 必须填对**：填得比模型实际能吃下的大，阈值也会跟着变大，压缩就会来得太晚。
